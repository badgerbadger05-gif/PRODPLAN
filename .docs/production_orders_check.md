# Учет заказов на производство при расчете потребностей

## 0) Важно: разделение сущностей (зафиксировать)

В проекте есть **две независимые группы заказов**:

1) **Заказы в 1С (УНФ)** — документы `Document_ЗаказНаПроизводство`.
   - Мы их используем **только как входные данные** для расчёта (read-only).
   - Мы **не создаём** их из PRODPLAN и **не обновляем** их из PRODPLAN.
   - Между заказами 1С и заказами PRODPLAN сейчас **нет связи/маппинга** (нет `prodplan_order_id -> 1c_ref` и обратно).

2) **Заказы PRODPLAN (плановые)** — сущности/таблицы проекта (например, создаваемые в процессе MRP как `planned_orders`).
   - Они живут в нашей БД и используются для планирования.

Следствие для задачи:
- Мы не «синхронизируем заказы» между системами.
- Мы **корректируем потребность** в расчёте, учитывая, что в 1С уже есть активные заказы (и часть из них может быть частично выполнена).

## 1) Цель и итоговое правило (коротко)

Цель: при расчёте потребностей (MRP) **не планировать выпуск/закупки сверх того, что уже покрывается активными производственными заказами в 1С**, и **не считать доступными те материалы**, которые уже «заняты» активными производственными заказами 1С.

Итоговое правило:
- Учитываем **все активные** заказы на производство из 1С.
- «Закрыт» для этой задачи = **состояние/статус заказа в 1С = «Завершен»**.
- `Posted` / `is_posted` **НЕ** используется для определения «закрыт/активен».
- Заказы могут быть **частично выполнены**: в расчётах используется **только остаток к выпуску** по строкам.

## 2) Термины и статусы (зафиксировать в коде/БД)

### 2.1 Что считаем «активным заказом 1С»

- **Активный** — заказ 1С, который должен участвовать в расчётах потребностей.
- **Закрытый** — заказ 1С, который **не** должен участвовать в расчётах.

### 2.2 Как в 1С (УНФ) определяем «закрытый»

Подтверждено: «закрыт» в терминах задачи означает: **`СостояниеЗаказа == "Завершен"`**.

Техническая привязка к OData (по метаданным):
- Сущность заказа: `Document_ЗаказНаПроизводство` — см. [`output/odata_metadata.xml:23212`](output/odata_metadata.xml:23212).
- Признак проведения `Posted` присутствует — см. [`output/odata_metadata.xml:23232`](output/odata_metadata.xml:23232), **но не используется** для определения «активный/закрыт».
- Состояние заказа — это ссылка:
  - `СостояниеЗаказа_Key` — см. [`output/odata_metadata.xml:23265`](output/odata_metadata.xml:23265)
  - navigation `СостояниеЗаказа` — см. [`output/odata_metadata.xml:23384`](output/odata_metadata.xml:23384)

### 2.3 Константа DONE_STATE_KEY

В нашем окружении GUID состояния «Завершен» уже выявлен:
- `DONE_STATE_KEY = ad28565a-991b-11eb-e39a-fa163e61326a` (см. [`.docs/production_orders_analysis.md`](.docs/production_orders_analysis.md:1)).

Правило фильтрации активных заказов 1С (каноническое):
- `deletion_mark == false`
- `order_state_key != DONE_STATE_KEY`

## 3) Область учёта активных заказов 1С (A/B)

Чтобы требование было однозначным, фиксируем, что активные производственные заказы 1С учитываются **в двух местах**:

**A) Как уже запланированный выпуск готовой продукции**
- Если на изделие уже есть активные заказы 1С, то новая потребность на выпуск этого же изделия уменьшается на суммарный остаток активных заказов 1С.

**B) Как потребление компонентов (занятие остатков)**
- Активные заказы 1С потребляют компоненты по спецификации и тем самым уменьшают доступность материалов для новых заказов PRODPLAN.

Если в будущем решим учитывать только A или только B — это нужно явно изменить в этом документе и в тест-кейсах.

## 4) Что меняем в коде (пошагово) — чтобы всё работало

Важно: согласно текущей архитектуре расчёта, компонентный лимит считается на подготовленных кэшах и далее используется внутри [`OrderQuantityCalculator`](backend/app/services/order_quantity_calculator.py:1). Поэтому изменения делаем так, чтобы:

- калькулятор **не** получал прямой доступ к БД;
- все «учёты активных заказов 1С» внедрялись на этапе подготовки входных данных к расчёту.

### Шаг 1. Уточняем модель/хранение заказов 1С в БД (как кэш для расчёта)

Примечание: таблицы `production_orders` / `production_products` в проекте трактуем как **кэш данных из 1С для расчётов**, а не как «заказы PRODPLAN».

Проблема сейчас: использовать `Posted` как «закрыт» нельзя.

Изменения в моделях/БД:

1) В таблицу `production_orders` добавить поля:

- `order_state_key` (GUID/строка из `СостояниеЗаказа_Key`)
- `order_state_name` (опционально, для диагностики; берём из `$expand=СостояниеЗаказа`)
- `deletion_mark` (bool из `DeletionMark`)

2) Добавить миграцию Alembic.

3) Обновить SQLAlchemy модель (см. [`ProductionOrder`](backend/app/models.py:1)).

4) Обновить Pydantic-схемы (см. [`ProductionOrderBase`](backend/app/schemas.py:1)):

- новые поля сделать **optional**, чтобы не ломать существующие контракты.

### Шаг 2. Обновляем загрузку/кэширование заказов 1С: подтягиваем состояние заказа

Файл: [`production_order_sync.py`](backend/app/services/production_order_sync.py:1).

Что делаем:

1) В OData-запрос по `Document_ЗаказНаПроизводство` добавить поля:

- `СостояниеЗаказа_Key`
- `DeletionMark`
- опционально: `$expand=СостояниеЗаказа` (чтобы вытянуть человекочитаемое описание).

2) На upsert заказа сохранять:

- `order_state_key = record['СостояниеЗаказа_Key']`
- `order_state_name = record['СостояниеЗаказа']['Description']` (или другое поле, которое реально отдаёт стенд)
- `deletion_mark = record.get('DeletionMark', False)`

3) **Не** пытаться выводить «активность» из `Posted`.

Важно: этот шаг не создаёт связь с заказами PRODPLAN — это просто кэш статуса заказов 1С для корректировки расчёта.

### Шаг 3. Нормализуем хранение строк заказа 1С (иначе остатки будут неверны)

Проблема: один заказ 1С может содержать несколько строк одного и того же изделия и/или разрез по характеристикам. Если у нас ключ строки не хранится, мы не сможем корректно сопоставить «заказано» и «выпущено».

Изменения:

1) В `production_products` добавить:

- `line_number` (int из `LineNumber` табличной части заказа)
- `characteristic_ref1c` (GUID из `Характеристика_Key`, nullable)

2) Ввести уникальность по строке:

- уникальный индекс/constraint по `(order_id, line_number)`.

3) В синхронизации табличной части заказа `Document_ЗаказНаПроизводство_Продукция` сохранять `line_number` и `characteristic_ref1c`.

### Шаг 4. Добавляем факт выпуска по заказам 1С: produced_qty и remaining_qty

Требование: активные заказы 1С могут быть частично выполнены ⇒ нужен `produced_qty`, а из него — `remaining_qty`.

Источник факта выпуска (подтверждено): документы `Document_СборкаЗапасов`, связанные с заказом полем `ЗаказНаПроизводство_Key` (см. [`.docs/production_orders_analysis.md`](.docs/production_orders_analysis.md:1)).

Рекомендуемая реализация:

1) Храним факты на уровне строки заказа 1С:

- либо расширяем `production_products` колонками `produced_qty`, `remaining_qty`;
- либо вводим отдельную таблицу фактов.

2) Добавляем сервис загрузки фактов выпуска, который:

- грузит `Document_СборкаЗапасов` по активным заказам 1С;
- читает `Document_СборкаЗапасов_Продукция`;
- агрегирует `produced_qty` по ключу сопоставления;
- пишет `produced_qty` и вычисляет `remaining_qty`.

3) Зафиксировать правило: учитывать ли только `Posted == true` у `Document_СборкаЗапасов`.

### Шаг 5. Меняем планирование PRODPLAN: учитываем активные заказы 1С в A и B

Ключевой слой внедрения — планирование (а не «синк между системами»).

#### 5.1 Учёт A (уменьшение потребности на выпуск изделия)

Где: в [`build_planned_orders_and_purchases()`](backend/app/services/planning_service.py:1736) перед расчётом количества нового заказа.

Как:

1) Для текущего `item_id` посчитать `active_remaining_qty` как сумму `remaining_qty` по активным строкам заказов 1С.
2) `requested_qty_adj = max(requested_qty - active_remaining_qty, 0)`.
3) Дальше расчёт вести от `requested_qty_adj`.

#### 5.2 Учёт B (занятие компонентов активными заказами 1С)

Где: при подготовке `stock_by_item` до создания/использования [`OrderQuantityCalculator`](backend/app/services/order_quantity_calculator.py:1).

Как:

1) Собрать активные строки заказов 1С с `remaining_qty > 0`.
2) Для каждой строки определить спецификацию изделия (зафиксированная в строке, иначе дефолтная).
3) Посчитать потребность в компонентах исходя из `remaining_qty`.
4) `reserved_by_component[child_id] += remaining_qty * qty_per_unit`.
5) `effective_stock_by_item[child_id] = max(stock_by_item[child_id] - reserved_by_component[child_id], 0)`.
6) В расчётах использовать `effective_stock_by_item`.

### Шаг 6. Тесты

1) A: активный заказ 1С уменьшает потребность по изделию.
2) B: активный заказ 1С занимает компоненты.
3) «Завершен» не влияет.
4) Частичное выполнение учитывается по `remaining_qty`.

## 5) Блок: Логика расчёта remaining_qty (каноническая)

### 5.1 Определения

- `ordered_qty` — количество по строке заказа 1С.
- `produced_qty` — фактически выпущенное количество по этой строке (агрегат по связанным документам выпуска).
- `remaining_qty` — остаток к выпуску по строке.

### 5.2 Формула

`remaining_qty = max(ordered_qty - produced_qty, 0)`

### 5.3 Ключ агрегации produced_qty

Предпочтительно агрегировать по `(order_ref1c, line_number)` с дополнительной сверкой `item_ref1c`/`characteristic_ref1c`.

### 5.4 Применение A/B

- A: `new_need_X = max(new_need_X - Σ remaining_qty(active, X), 0)`
- B: `reserve_c += remaining_qty(X) * qty_per_unit_c`
