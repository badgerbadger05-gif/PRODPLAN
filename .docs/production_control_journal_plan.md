# Журнал заказов на производство: целевой контур

## Цель

Журнал заказов становится рабочим контуром между MRP, складом, цехом и 1С:

1. MRP рассчитывает потребность, даты запуска/окончания, мощности и дефициты.
2. Продплан создает внутренние заказы на производство из MRP-строк.
3. Эти заказы учитываются в следующих MRP-расчетах как активное ожидаемое производство.
4. В журнале пользователь запускает выбранные строки в 1С.
5. Продплан создает в 1С заказ на производство и сразу проводит его оперативно через `Post?PostingModeOperational=true`.
6. На основании заказа Продплан создает непроведённое перемещение компонентов и добавляет его в журнал заявок на перемещение.
7. Кнопка `Собрано` в журнале перемещений проводит перемещение через `Unpost` + `Post?PostingModeOperational=true` и возвращает в журнал заказов обеспечение `Собрано`.
8. Продплан обновляет состояние по факту проверенных документов и движений 1С.

## Принятые правила

- Прямой деплой на прод мимо GitHub запрещен без отдельного явного разрешения.
- Документы в 1С из Продплана создаются только по явной кнопке пользователя в журнале, без массовой фоновой write-выгрузки.
- Документы сначала создаются непроведенными (`Posted=False`), затем проводятся только штатной OData-командой, если для типа документа подтверждён рабочий сценарий проведения.
- Документы в 1С создаются “на основании” родительского документа бизнес-цепочки:
  - перемещение компонентов — на основании `Document_ЗаказНаПроизводство`;
  - выпуск/сборка — на основании `Document_ЗаказНаПроизводство`;
  - сдельный наряд — на основании `Document_СборкаЗапасов`.
- Технически основание передаётся через `ДокументОснование` и `ДокументОснование_Type`; без подтверждённого основания дочерний документ не выгружается.
- Для `Document_ПеремещениеЗапасов` подтверждён рабочий сценарий: дата документа текущая, затем `POST .../Unpost` и `POST .../Post?PostingModeOperational=true`; прямой `PATCH Posted=true` запрещён.
- Для повторного нажатия нужна идемпотентность: один `PlannedOrder` не должен создавать несколько внутренних заказов.
- Внутренние заказы Продплана хранятся в тех же таблицах, что и заказы 1С:
  - `production_orders.source = 'mrp'`;
  - `production_orders.source_run_id = planning_run.run_id`;
  - `production_products.source_planned_order_id = planned_order.order_id`.

## Состояния обеспечения

Колонка журнала называется **Обеспечение**.

Статусы:

- `Дефицит` (`shortage`) — нет обеспечения по одному или нескольким компонентам.
- `Частично` (`partial`) — часть компонентов есть, но не на весь заказ.
- `Обеспечен` (`ready`) — компонентов хватает на разрешенных складах.
- `К перемещению` (`to_move`) — заказ на производство проведён, перемещение создано в 1С непроведённым и ожидает сборки.
- `Собрано` (`assembled`) — перемещение проведено из журнала перемещений кнопкой `Собрано` или найдено проведенным при синхронизации.

## Журнал заявок на перемещение

Журнал заявок на перемещение — отдельная рабочая страница склада. В левом списке отображаются созданные `production_material_issues` и их 1С-ссылки, в правом окне — детали к сборке: изделие, заказ, склады отправителя/получателя и комплектующие.

Основной поток:

1. В журнале заказов пользователь нажимает `Запустить в 1С`.
2. PRODPLAN создаёт/переиспользует локальную заявку перемещения, выгружает родительский заказ на производство и проводит его оперативно.
3. PRODPLAN выгружает `Document_ПеремещениеЗапасов` непроведённым и оставляет строку в журнале перемещений со статусом `В 1С`.
4. После физической сборки пользователь нажимает `Собрано`; PRODPLAN штатно проводит перемещение в 1С и ставит заказу обеспечение `Собрано`.
- `Произведен частично` (`produced_partial`) — выпуск меньше заказа.
- `Произведен` (`produced`) — выпуск закрыл заказ.

Отдельный статус `Перемещается` не используется: он дублирует `К перемещению`.

## Настройки

В журнале есть окно настроек:

- привязка `участок -> склад получатель`;
- список игнорируемых складов.

Игнорируемые склады нужны, чтобы не задавать лишние вопросы по остаткам, например если компонент лежит в изоляторе брака.

## Целевой UX процесса

Пользователь работает не с массовой выгрузкой, а с конкретной цепочкой:

1. `Запустить в 1С` на выбранном заказе или строке: Продплан создаёт недостающий `Document_ЗаказНаПроизводство`, проводит заказ оперативным OData-методом, создаёт непроведённый `Document_ПеремещениеЗапасов` и оставляет строку в статусе ожидания сборки.
2. `Произвести`: пользователь вводит количество и исполнителя; Продплан создаёт и проводит `Document_СборкаЗапасов`, затем создаёт и проводит `Document_СдельныйНаряд` на основании сборки.
3. Повторное нажатие не создаёт дубль: цепочка поднимается из `sync_link` и продолжает недостающий шаг либо показывает ошибку.
4. Фоновые задачи читают 1С: справочники, остатки, проведённые документы и факты. Они не создают документы в 1С.
