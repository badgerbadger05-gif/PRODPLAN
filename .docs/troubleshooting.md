```bash
ssh barsukov@mtzdock.lan
```

## Planning truth

При неверных цифрах сначала проверяются принятое поколение Ledger, cutoff и
freshness, полнота физического Ledger, опубликованная read-model и чтение
остатков из принятого поколения. Нельзя переключаться на legacy-остатки или
использовать старый контур как второй источник истины.

## Поступление задним числом, поглощённое снапом cutoff

Признак: склад принял документ, физический остаток верный, а «к заказу» по тем
же позициям не уменьшилось. В леджере нет строк с `recorder_ref` этого
документа, зато на те же ячейки в тот же день стоят строки
`cutoff_balance_adjustment` на ту же сумму.

Причина: 1С хранит в регистре дату **документа** (`Period`), а не момент
записи. Документ, введённый после принятого cutoff, но датированный раньше
него, попадает в уже закрытое окно прямого импорта; штатный аудит тянет только
явно поставленные в очередь регистраторы, а поступление, набранное человеком в
1С, никто не ставит в очередь. Баланс расходится, и снап закрывает расхождение
синтетической строкой, которую атрибуция пополнения не читает.

Штатный физический refresh чинит этот класс сам: при несведённом балансе он
сначала запрашивает регистр по несошедшимся позициям и дотягивает реальные
регистраторы (`_repair_mismatched_recorders`), гасит снап, который их поглощал
(`retire_cutoff_snaps_absorbing_facts` — операция балансово-нейтральна:
необъяснённый остаток снапа переиздаётся), и только потом снапит то, чего не
объяснил ни один документ 1С.

Уже поглощённое так не чинится: такие ячейки сходятся с 1С, и никакого
расхождения, указывающего на них, больше нет. Для них есть разовый шаг с
остановленными писателями (он же пересобирает R4 существующими писателями
фазы `replenishment-rebase`, второго движка нет):

```bash
python tools/current_execution_migration.py --phase backdated-recorder-repair \
  --writers-stopped \
  --recorder "Document_ПриходнаяНакладная:<Ref_Key>" \
  --recorder "Document_ПриходнаяНакладная:<Ref_Key>"
```

Шаг не двигает указатель истины, не создаёт поколений и ничего не пишет в 1С.
Он отказывается работать, если ввозимые факты больше снапов на тех же ячейках:
это означало бы, что документ снапом не поглощался и его учёт удвоил бы
остаток.

Полное развёртывание описано только в
[prodplan-shadow-deploy.md](prodplan-shadow-deploy.md).
