# Локальный рефакторинг исполнения: тесты до реализации

Основание: решение владельца от 2026-09-10 — отдельная локальная ветка, прод не трогать, ожидания тестов фиксировать до реализации.

Полная последовательность перехода, целевой результат и общие критерии приёмки: [roadmap рефакторинга](current-execution-roadmap.md). Этот документ описывает первый тестовый участок и не заменяет roadmap.

## Первая поставка

Чистый план изменений количественных назначений в существующем каноническом historical_replay_core. Он переиспользует адресный FIFO, не создаёт второй движок и не подключается к рабочему API до появления транзакционного хранения. Входы — полный согласованный набор нормализованных фактов, резервов и предыдущих назначений одной обрабатываемой области. Пустой вход означает явно пустую область, а не неуспешный импорт. Проверка принятия источника должна предшествовать вызову в будущем сервисе.

Результат различает вставки, изменения существующей пары факт/резерв и удаления. Неизменившиеся назначения не требуют записи. При замене версии факта старые основания удаляются из текущего набора, но будущий слой хранения обязан сохранить историю изменения оснований. Эта функция сама историю не удаляет и БД не пишет.

Числовые ожидания в test_execution_change_contract.py заданы вручную; тесты не вычисляют ожидаемое через проверяемый allocator. Тестовый коммит должен предшествовать реализации. Начальный красный прогон подтверждает отсутствие нового контракта; один missing-symbol red не доказывает полноту тестов. После реализации обязательна проверка намеренным нарушением поведения (mutation probes) без изменения ожидаемых значений.

## Обязательные следующие проверки до переключения хранения

| Контракт | Вид проверки |
|---|---|
| Устойчивые ID резервов, неизменность frozen-потребностей после 100 повторов | Интеграционная, реальная локальная PostgreSQL |
| Нет роста числа текущих строк/снимков при повторе импорта | Подсчёт строк до/после; запрет создания поколений этим путём |
| Основания, исполнение и маркер импорта фиксируются вместе | Сбой в середине транзакции; отдельная читающая сессия |
| Два конкурентных распределения не тратят факт дважды | Две реальные транзакции PostgreSQL; SQLite не заменяет проверку |
| Недоступный/частичный источник не обнуляет исполнение | API/service тест до вызова чистого ядра |
| Отмена поступления, возврат по исходному документу и newest-first без ссылки | Нормализация и распределение вместе; три независимых сценария |
| Смена MRP, выпуск на границе фиксации, чужие планы | Проверки сохранённого выпуска и принадлежности факта |
| Поступление не освобождает удержание склада; расход освобождает | Отдельные предметные примеры |
| Старое исправление задевает последующий FIFO, но не чужой пул | Реальные назначения и аудит причин изменения |
| GET показывает итоги и основания одного состояния | Тест API с конкурентной публикацией, без запуска тяжёлого расчёта в GET |
| Экспортные ссылки и идемпотентность переживают миграцию ID | Миграционный тест на синтетических данных, без вызова 1С |
| Коррекция закрытого плана и custody rewind | Сначала явные ожидаемые бизнес-результаты, затем интеграционные тесты |

## Границы

Первая поставка не означает готовность новой модели хранения. Не меняет канон рабочих читателей и поколений. Следующая поставка обязана менять контракт и существующих писателей/читателей согласованно, а не оставлять два источника исполнения. Продовые SSH, базы, OData, публикации и push не нужны для этой работы.
