# Журнал исполнения — план улучшения читаемости (UX)

Постановка: **2026-06-11**. Проблема: журнал исполнения (вкладка в «Период план», `PeriodPlanPage.tsx`, API `GET /v1/plan/period-plans/{plan_id}/execution-journal`) показывает данные непонятно для пользователей.

## Диагноз: почему непонятно

1. **Шесть числовых колонок без явного статуса.** Потребность / Чистая потребность / Оформлено / Не оформлено / Выполнено / Осталось — пользователь должен сам в уме выводить состояние строки. В фильтре статусы есть («Закрыто», «Частично», «Оформлено», «Без заданий»), а в таблице колонки «Статус» нет.
2. **Термины не объяснены.** «Потребность» vs «Чистая потребность», «Выполнение %» (от какой базы?) — нет тултипов, пользователи не знают, что чистая = брутто − склад.
3. **Сводка — мелкий текст в командной строке.** «Общее выполнение: 87% Производство: … Закрыто: 12/40» — сливается с кнопками, не читается как сводка.
4. **Раскрытые work items переиспользуют колонки с другой семантикой.** В подстроке числа стоят под заголовками «Оформлено/Не оформлено», но означают «оформлено/не оформлено по заданию», дата потребности попадает в колонку «Выполнение». Нет подписей.
5. **Нет сроков в основной строке.** Дата потребности и прогноз видны только в раскрытии; пользователь не видит «успеваем или нет» без клика.
6. **Шум от строк с нулевой чистой потребностью** (покрыто складом) — они визуально равноправны с проблемными.

## Предложения (по убыванию эффекта)

### 1. Явная колонка «Статус» (фронт)
Вычислять тот же статус, что уже используется в фильтре, и показывать цветной пилюлей в строке:
- `Закрыто` (зелёный) — remaining ≤ 0;
- `Частично` (жёлтый) — completed > 0, remaining > 0;
- `Оформлено` (синий) — ordered ≥ net, completed = 0;
- `Не оформлено` (красный) — unassigned > 0;
- `Покрыто складом` (серый) — net = 0.

### 2. Сократить числовые колонки, остальное — в тултип/раскрытие
Видимые по умолчанию: **Чистая потребность → Оформлено → Выполнено → Осталось → Статус → Срок**. «Потребность (брутто)» и «остаток склада» — в title строки или в раскрытии (`gross_qty`, `stock_qty` уже приходят с бэка). «Не оформлено» поглощается статусом + красным числом в «Оформлено» (например «80 из 100»).

### 3. Колонка «Срок» в основной строке
`need_date` (мин. по work items, бэк может отдавать на строке) + прогноз сдвига: «25.06 (+4 дн)» красным при опоздании. Сейчас `forecast_date`/`forecast_shift_days` уже есть в ответе — нужна только колонка.

### 4. Сводка отдельной полосой, кликабельная
Вместо `toolbarText` — компактная полоса карточек под командной строкой: Общее выполнение (прогресс-бар), по потокам, счётчики «Закрыто / Частично / Не начато». Клик по счётчику применяет соответствующий фильтр статуса.

### 5. Читаемое раскрытие заданий
Подстроки с собственными подписями значений («оформлено 50 · выполнено 20 · осталось 30 · срок 25.06»), статус-пилюля для всех типов заданий (сейчас только production_order и planned_purchase), отступ и линия-коннектор. Не растягивать числа по колонкам родителя.

### 6. Тултипы на заголовках колонок
Однострочные пояснения терминов прямо в `title` заголовка (дёшево, снимает большинство вопросов «что это за число»).

### 7. Скрывать «Покрыто складом» по умолчанию
Чекбокс «Показывать покрытые складом» (выкл. по умолчанию) — журнал сразу показывает только то, с чем нужно работать.

## Объём изменений

- Почти всё — **только фронт** (`PeriodPlanPage.tsx`, doctype колонок). Бэк уже отдаёт все нужные поля.
- Бэк (мелочь): добавить в строку журнала `need_date` (мин. дата потребности требования) и готовый `status`, чтобы фронт и фильтр не дублировали логику — `period_plan_service.get_period_plan_execution_journal()`.
- Контракт API не ломаем — только добавляем поля.

## Порядок внедрения

1. Статус-колонка + тултипы + скрытие net_zero (быстрые победы, один PR).
2. Перекомпоновка колонок + колонка «Срок» (+ `need_date`/`status` на бэке).
3. Сводка-полоса с кликабельными счётчиками.
4. Редизайн раскрытия work items.
