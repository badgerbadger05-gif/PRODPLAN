# Runbook переключения PRODPLAN на release 05d7b375 — 2026-10-01

Операционная процедура, выстроенная по итогам двух staged-репетиций
(30.09 и 01.10) на реальных данных emergency. Статус: проверяется,
тайминги — измеренные. Отменяет порядок «rebase до refresh» из
readiness-decision 29.09: на живых данных он неработоспособен (см. §2).

**Решение владельца 02.10:** производственные окна только на выходных.
Подготовка выполняется локально; весь код, проверяющие инструменты и этот
runbook должны быть в `main` и опубликованы в remote до работы из дома.
Локальная копия, полученная без fence, служит только репетиции и не является
готовым пакетом переключения. Актуальный порядок подготовки — §5.

## 1. Диск — жёсткое требование

Перед окном на сервере должно быть свободно ≥ 25 ГБ: дамп (~4,5 ГБ) +
restore (~17 ГБ) + WAL/temp миграции (~3 ГБ пик). На 01.10 свободно ~4–9 ГБ
после чисток; emergency pgdata (19,6 ГБ) — неприкосновенный откат до
подтверждения переключения. Проверка: `df -h /`.

В миграции обязательно `maintenance_work_mem = '2GB'` на целевой БД
(ALTER DATABASE … SET) — иначе построение `ux_stock_bin_generation_key`
сливает temp на диск и роняет postgres при нехватке места (инцидент
репетиции 30.09, 15:50).

## 2. Процедура fence — исправлена

Дамп 30.09 12:05 оказался непригодным для rebase: 4-минутный хвост
командных custody-событий (`issue_created` 5390–5394 между принятием g1604
и fence) — bounded refresh отказывается поглощать нефизический хвост
(`custody tail contains a non-physical event`), rebase требует
`source_event_high_watermark_id = max(custody_event.id)`.

Правильный порядок окна:

1. Объявить обслуживание, вывесить maintenance-страницу на :9020.
2. Запретить новые операторские команды (стоп frontend/backend emergency —
   sync-worker пока работает).
3. **Дождаться принятого поколения emergency, у которого
   `production_material_custody_projection_manifest.source_event_high_watermark_id
   = (SELECT max(id) FROM production_material_custody_event)`** — все
   read-back последних команд поглощены. Обычно один цикл refresh (~15 мин).
4. Стоп sync-worker emergency. Дамп (`pg_dump -Fc --no-owner --no-acl`).
5. Дальше без прода: restore в `prodplan_prod_20260930` → миграция
   (`PGOPTIONS=-c prodplan.execution_projection_backup_ready=on`, скрипт со
   стражами) → staged physical refresh (доест физический хвост, если появился
   за время дампа) → canonical §58 rebase на новом принятом поколении →
   republish → API-гейты → переключение :9020 на новый frontend →
   sync-worker профиля autoworker → визуальный smoke → открыть операторам.

Откат на любом шаге до переключения порта: emergency-БД не изменялась —
старт старых контейнеров возвращает прод за минуты.

## 5. Локальная подготовка и переключение в выходные

### До производственного окна

1. Свести release-кандидат и исправления в `main`, выполнить полный pytest
   с итогового коммита, проверить frontend build и опубликовать `main`.
   Домашний checkout, backend/worker image и deployment receipts должны
   указывать один и тот же итоговый SHA. Не переносить секреты, дампы или
   runtime `sync_schedule.json` через Git.
2. Получить свежий custom-format дамп emergency в локальное хранилище
   потоково: серверный `pg_dump` отдаёт stdout по SSH, поэтому на сервере
   не создаётся ещё одна копия дампа. Зафиксировать SHA256, размер, время
   и признак отсутствия fence. Restore выполнить в новую изолированную
   loopback PostgreSQL-БД; существующие рабочие БД и тома не сбрасывать.
3. На остановленной локальной копии выполнить capture-before через
   `tools/operational_preservation.py`, Alembic до `20260911_01`, existing
   current-owner preflight/apply/postflight, Alembic head, verify-after.
   Проверка выполняется до изменения факта refresh/rebase; старый failed
   receipt от 01.10 не считать доказательством сохранности.
4. Выполнить canonical physical refresh, §58 rebase и republish в порядке §2,
   проверить 11 ready scopes и физический fold по выбранным складским ключам.
   Проверить два следующих обычных refresh с реальной дельтой: отсутствие
   зависшего BUILDING, rejected/error и повторного row/audit churn.
   Не выдавать отсутствие новой дельты за доказательство этих двух циклов.
5. Уменьшение данных доказать замерами `pg_database_size`, размеров таблиц,
   current/evidence row counts и размера custom dump до/после. Миграция
   удаляет устаревшие проекции; PostgreSQL-файлы после DELETE могут сохранять
   выделенное место. Локальный manifest-first GC и отдельный reclaim применять
   только по `docs/accepted-generation-gc-runbook.md` после verified backup.
   Не удалять accepted физические факты, operator history или unknown-FK
   dependencies. Затем восстановить компактный дамп в ещё одну пустую локальную
   БД и повторить приёмку: это одновременно проверяет archive и фактический
   размер будущего restore. Синтетический seed не заменяет этот gate.

### В выходное производственное окно

1. Fence выполняется на emergency по §2: запретить команды, дождаться
   accepted custody HWM = max(event.id), остановить всех writers. Записать
   exact accepted pointer, cutoff, HWM и контроль операторских данных.
2. Снять новый fenced дамп и выполнить локально уже проверенный конвейер.
   Дневную unfenced копию нельзя просто выгрузить поверх прода: новые команды
   в emergency не являются исключительно физическим OData-хвостом.
   Инкрементальный перенос этих команд не реализован этой процедурой.
3. Проверенный компактный пакет включает dump SHA256/размер, исходный fenced
   SHA256, source pointer/cutoff/HWM, итоговый Git/image SHA, preservation,
   physical/read-model/API receipts и successful compact restore receipt.
   Перед переносом повторно доказать, что emergency оставался fenced и его
   pointer/операторский контроль не изменились.
4. На сервере выполнить только restore проверенного компактного пакета в
   целевую БД, HTTP/API и визуальную проверку, затем открыть операторов.
   Требование §1 ≥25 ГБ относится к полному серверному dump/restore/migration;
   для компактного пути отдельно доказать запас диска из измеренного compact
   restore плюс archive, WAL/temp и safety reserve. Без такого proof сохраняется
   прежний жёсткий блокер §1; оценка по одному размеру сжатого dump запрещена.
5. Emergency pgdata сохранить как исходный откат. Если окно прервано и emergency
   снова открыт операторам, подготовленный пакет устаревает: его source chain
   нужно построить заново, а не открывать поверх него запись.

Подготовка, загрузка файлов и локальные тесты в будни не являются разрешением
на fence, GC emergency или переключение порта в будни. Срок окна уточняется
после измеренной свежей локальной репетиции; прежние 4,5–5 ч — исторический
замер серверного конвейера, а не обещание нового локального сценария.
