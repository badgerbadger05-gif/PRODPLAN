# PRODPLAN — действующие решения владельца

Этот файл содержит только действующие решения.

## 1. Граница с 1С

1. 1С создаёт физические движения.
2. PRODPLAN зеркалит физику read-only.
3. PRODPLAN создаёт планы, резервы, потребности и рабочие предложения.
4. Резервы не экспортируются в 1С.
5. Заказ не является фактом выпуска или поступления.
6. По явной команде оператора PRODPLAN создаёт исполнительные документы в 1С
   через санкционированные точки экспорта. В их числе выпуск: кнопка
   «Произвести» одним действием создаёт `СборкаЗапасов` и `СдельныйНаряд`,
   1С их проводит, PRODPLAN сразу считывает регистр проведения и записывает
   факт через Item Ledger. Фактом является только считанный назад результат
   проведения; создание документа фактом не является. Удаление этого контура
   запрещено.

## 2. Две ленты номенклатуры

У каждой карточки:

1. лента физического количества;
2. лента резервов живых планов.

Все количественные отчёты являются проекциями этих двух лент одного
принятого поколения.

## 3. Фиксация плана

План фиксируется один раз. В одном действии:

- сохраняется выпуск готовых изделий;
- разворачивается BOM;
- фиксируется полный резерв;
- фиксируется покрытие наличием;
- фиксируется потребность пополнения;
- создаются рабочие строки `make/buy`;
- выпуск добавляется в общую очередь сборки.

Повторного MRP фиксированного плана нет.

## 4. Резервы

Полная потребность BOM резервируется независимо от наличия.

Покрытие наличием и потребность пополнения фиксируются на cutoff и не
переписываются. Новый план создаёт новый резерв. Резервы старых живых планов
имеют приоритет.

## 5. Пополнение

`make` и `buy` только выбирают журнал. Математика одна.

Выполнение — покрытая физическими пополнениями часть исходной потребности:

```text
execution_qty =
    min(replenishment_received_qty, replenishment_required_qty)

execution_pct =
    execution_qty / replenishment_required_qty * 100
```

`execution_pct` измеряется в процентах от 0 до 100. Если пополнение не
требовалось, процент отсутствует.

## 6. FIFO

Положительный выпуск или приход распределяется по старейшим живым
потребностям номенклатуры. Меньший факт частично закрывает старшую
потребность, излишек переходит следующей.

Связь с заказом — provenance. Неизвестность связи не блокирует FIFO.

## 7. Очередь сборки

Очередь состоит из остатка верхнеуровневого выпуска всех живых планов:

```text
assembly_remaining_qty =
    max(planned_output_qty - accepted_plan_output_qty, 0)
```

Старый план находится раньше нового. Недовыполнение старого плана не
переносится в новый и не исчезает при появлении нового.

Ручной производственной программы для барабана нет.

## 8. Барабан

Барабан раскладывает единую очередь сборки от текущей даты вперёд по участкам,
тактам, календарю и мощности.

Плановые количества неизменяемы. Календарная раскладка подвижна.
Невыполненное переносится вправо. Плитку закрывает только принятый физический
выпуск, а не создание или release заказа.

При точной связи выпуск закрывает свой план. Без точной связи закрывается
старейшая открытая строка этого изделия FIFO.

Барабан не разворачивает BOM, не создаёт резервы и не рассчитывает
потребность.

## 9. Закрытие

Просрочка не закрывает план. При явном закрытии его резервы и строки сборки
удаляются из рабочих очередей. Исходные цифры и недовыполнение остаются в
историческом снимке.

## 10. Полки и мехцех

MRP определяет общее количество производства детали. DBR не создаёт
дополнительную потребность.

Полка удерживает ту часть незакрытой потребности, которая будет потреблена
барабаном внутри защитного окна:

```text
protection_days =
    replenishment_time + review_cycle + safety_days
```

Длинная видимая серия формирует более уверенное удержание полки. Малая серия
автоматически ограничивает target своим остатком. Target никогда не превышает
незакрытую потребность живых планов.

DBR задаёт мехцеху срок, приоритет и количество текущего вытягивания.
`confirmed_open_production_qty` — количество незакрытых исполнительных строк
производства, связанных с этим требованием, имеющих подтверждённый срок и
склад назначения. Оно вычитается перед новым вытягиванием. Количество заказа
не может превысить незапущенный остаток MRP.

## 11. Истина

Только принятое поколение Item Ledger является источником физического факта.
Плановый снимок хранит обязательство.

Пустое, неполное, непринятое, отозванное или stale поколение даёт
`unavailable`.
Legacy fallback запрещён.
