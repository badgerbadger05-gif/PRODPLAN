# Учет заказов 1С при расчете потребностей

## Разделение сущностей

1) **Заказы в 1С (УНФ)** — документы `Document_ЗаказНаПроизводство`
   - Используем **только как входные данные** для расчёта (read-only)
   - **Не создаём** и **не обновляем** из PRODPLAN
   - **Нет связи** с заказами PRODPLAN

2) **Заказы PRODPLAN (плановые)** — сущности проекта (`planned_orders`)
   - Живут в нашей БД и используются для планирования

Следствие:
- Не «синхронизируем заказы» между системами
- **Корректируем потребность** в расчёте, учитывая активные заказы в 1С

## Цель и правила

Цель: при расчёте потребностей (MRP) **не планировать выпуск/закупки сверх того, что уже покрывается активными производственными заказами в 1С**, и **не считать доступными материалы**, занятые активными заказами 1С.

Правила:
- Учитываем **все активные** заказы на производство из 1С
- «Закрыт» = **состояние заказа в 1С = «Завершен»**
- `Posted` / `is_posted` **НЕ** используется для определения «закрыт/активен»
- Заказы могут быть **частично выполнены**: в расчётах используется **только остаток к выпуску**

## Термины и статусы

### Что считаем «активным заказом 1С»

- **Активный** — заказ 1С, который должен участвовать в расчётах потребностей
- **Закрытый** — заказ 1С, который **не** должен участвовать в расчётах

### Определение «закрытого» в 1С

Подтверждено: «закрыт» = **`СостояниеЗаказа == "Завершен"`**

Технически:
- `СостояниеЗаказа_Key` — GUID состояния заказа
- `Posted` — признак проведения, **не используется** для определения активности

### Константа DONE_STATE_KEY

- `DONE_STATE_KEY = ad28565a-991b-11eb-e39a-fa163e61326a`
- Правило фильтрации активных заказов:
  - `deletion_mark == false`
  - `order_state_key != DONE_STATE_KEY`

## Область учёта активных заказов 1С (A/B)

Активные заказы 1С учитываются **в двух местах**:

**A) Как уже запланированный выпуск готовой продукции**
- Если на изделие уже есть активные заказы 1С, то новая потребность на выпуск этого изделия уменьшается на суммарный остаток активных заказов 1С

**B) Как потребление компонентов (занятие остатков)**
- Активные заказы 1С потребляют компоненты по спецификации, уменьшая доступность материалов для новых заказов PRODPLAN

### Шаг 5. Планирование PRODPLAN: учёт A и B

#### 5.1 Учёт A (уменьшение потребности на выпуск изделия)

В `build_planned_orders_and_purchases()`:
1) Для `item_id` посчитать `active_remaining_qty` как сумму `remaining_qty` по активным строкам заказов 1С
2) `requested_qty_adj = max(requested_qty - active_remaining_qty, 0)`
3) Дальше расчёт вести от `requested_qty_adj`

#### 5.2 Учёт B (занятие компонентов)

При подготовке `stock_by_item` до использования `OrderQuantityCalculator`:
1) Собрать активные строки заказов 1С с `remaining_qty > 0`
2) Определить потребность в компонентах исходя из `remaining_qty`
3) `reserved_by_component[child_id] += remaining_qty * qty_per_unit`
4) `effective_stock_by_item[child_id] = max(stock_by_item[child_id] - reserved_by_component[child_id], 0)`
5) В расчётах использовать `effective_stock_by_item`

## Логика расчёта remaining_qty

### Определения

- `ordered_qty` — количество по строке заказа 1С
- `produced_qty` — фактически выпущенное количество по строке
- `remaining_qty` — остаток к выпуску по строке

### Формула

`remaining_qty = max(ordered_qty - produced_qty, 0)`

### Применение A/B

- A: `new_need_X = max(new_need_X - Σ remaining_qty(active, X), 0)`
- B: `reserve_c += remaining_qty(X) * qty_per_unit_c`
