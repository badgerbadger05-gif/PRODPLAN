# Ядро количества, резервов и пополнения

Это единственная нормативная модель количественного учёта PRODPLAN.

## Карточка номенклатуры

У каждой номенклатуры две ленты:

1. **Количество** — подписанные физические движения из 1С.
2. **Резервы** — количество, удерживаемое под каждый живой план.

Количество отвечает, сколько физически есть. Резервы отвечают, сколько и под
какой план удерживается, закупается или производится.

## Фиксация плана

Фиксация выполняется один раз и атомарно:

1. сохраняется исходный выпуск готовых изделий;
2. BOM разворачивается до полного набора потребностей;
3. для каждой номенклатуры читается количество на cutoff;
4. количество распределяется по живым резервам oldest-first;
5. для нового требования записывается полный резерв;
6. фиксируется покрытие наличием;
7. фиксируется недостающее пополнение.

```text
reserved_qty = полная потребность BOM

covered_from_stock_at_freeze_qty =
    min(reserved_qty, свободное количество после старших резервов)

replenishment_required_qty =
    reserved_qty - covered_from_stock_at_freeze_qty
```

Эти три величины не меняются до закрытия плана. Следующий план создаёт новый
резерв и не переписывает старый.

Полностью покрытая наличием позиция не попадает в рабочий журнал, но её резерв
остаётся активным.

## Единая потребность пополнения

Способ пополнения только выбирает исполнителя:

- `make` — журнал производства;
- `buy` — журнал закупки.

Оба журнала читают одну и ту же зафиксированную потребность. Собственных
формул потребности у них нет.

## FIFO пополнений

Каждый допустимый положительный физический выпуск или приход распределяется
по активным потребностям этой номенклатуры oldest-first:

```text
take = min(
    остаток физического пополнения,
    остаток потребности старшего резерва,
)
```

Меньший приход частично покрывает старший резерв. Излишек закрывает старший
резерв и переходит следующему. Остаток после всех потребностей становится
свободным количеством.

Точная ссылка на заказ сохраняется как происхождение факта. Если ссылка
неизвестна или неоднозначна, количество всё равно распределяется FIFO.
Произвольное адресное назначение запрещено.

## Резерв и выполнение

Резерв не уменьшается при поступлении:

```text
replenishment_remaining_qty =
    max(replenishment_required_qty - replenishment_received_qty, 0)

execution_qty =
    min(replenishment_received_qty, replenishment_required_qty)

execution_pct =
    execution_qty / replenishment_required_qty * 100
```

Выполнение — покрытая часть исходной потребности пополнения, а не всего BOM и
не всего резерва.

Если пополнение не требовалось, состояние —
`replenishment_not_required`; процент не вычисляется.

## Политика клампов

К нулю клампятся только остатки обязательств и выполнение, ограниченное
исходным обязательством:

```text
replenishment_remaining_qty >= 0
execution_qty <= replenishment_required_qty
0 <= execution_pct <= 100
assembly_remaining_qty >= 0
```

Физические и диагностические балансы не клампятся. `free_qty = on_hand -
active_reserved_qty` может быть отрицательным: это видимый дефицит, который
нельзя скрывать нулём.

## Новый план при недовыполнении

Незакрытая потребность старого живого плана остаётся в его резерве. Новый план
создаёт дополнительный резерв той же номенклатуры. Поэтому без отдельного
расчёта видно суммарное количество и распределение по планам.

Новый резерв не наследует и не изменяет резерв старого плана.

## Закрытие плана

Просрочка не закрывает план. План закрывается только явным действием.

При закрытии:

- его резервы исключаются из рабочего FIFO;
- исходные цифры плана и фактическое выполнение остаются историей;
- незакрытый остаток не переносится автоматически в другой план.

Рабочая строка резерва после закрытия больше не существует. История хранится
в неизменяемом снимке плана и событиях Ledger, а не в активной очереди.

## Инварианты

1. Один резерв принадлежит одному требованию одного плана.
2. Один физический факт назначается не более одного раза.
3. Сумма назначений не превышает количество факта.
4. FIFO общий для `make` и `buy`.
5. Журналы только проецируют сохранённые величины.
6. BOM не пересчитывается после фиксации.
7. Заказ и его статус не являются фактом выполнения.
8. При недоступном Ledger все зависимые величины `unavailable`.
