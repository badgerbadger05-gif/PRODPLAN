# Полки, буферы и вытягивание мехцеха

Этот документ задаёт целевую связь MRP, барабана и мехцеха.

## Граница ответственности

MRP владеет общим количеством детали на период:

```text
replenishment_required_qty
replenishment_received_qty
replenishment_remaining_qty
```

DBR не увеличивает и не уменьшает эти величины. Он определяет:

- когда деталь понадобится сборке;
- какую часть общей потребности пора держать на полке;
- какой производственной строке поднять приоритет;
- когда должен начаться выпуск мехцеха.

Буфер полки — временное размещение части уже существующей MRP-потребности, а
не дополнительный резерв и не новый спрос.

## Полка

Полка — настроенная физическая точка хранения производимой детали:

```text
item_id
warehouse_id
replenishment_time_days
review_cycle
safety_days
batch_multiple
active
```

`ShelfPolicy.replenishment_time_days` — локальная длительность производства
для защитного окна полки. Это не MRP-поле `Item.replenishment_time`: его
единственный источник — `СрокПополнения` номенклатуры 1С, включая валидный
ноль. Ни одно из этих полей не подменяет другое.

Состав полок является устойчивым справочником. Расчёт может предложить новую
полку, но не создаёт и не удаляет её автоматически при смене плана.

## Временной спрос

При фиксации MRP сохраняет происхождение каждого требования от
верхнеуровневой строки плана и норму детали на единицу изделия.

После раскладки барабана DBR переносит потребность детали на даты плиток:

```text
component_demand(slot) =
    slot_qty × frozen_component_qty_per_parent
```

Это календарная проекция уже зафиксированного требования. Повторной
BOM-развёртки и нового количества не возникает.

Спрос одной детали от всех плиток и всех живых планов агрегируется по датам с
сохранением плановой принадлежности.

## Размер буфера полки

На дату расчёта определяется защитное окно:

```text
protection_days =
    ShelfPolicy.replenishment_time_days + review_cycle + safety_days
```

Целевое количество на полке равно видимому расходу барабана внутри этого
окна:

```text
shelf_target_qty(today) =
    сумма незакрытого component_demand
    с need_date <= today + protection_days
```

Ограничения:

```text
0 <= shelf_target_qty <= незакрытая потребность всех живых планов
```

Если одинаковая техника идёт длинной устойчивой серией, в защитное окно
попадает больше подтверждённого расхода и полка удерживается увереннее.
Если впереди малая серия или конец выпуска, цель автоматически уменьшается.

DBR никогда не достраивает полку до абстрактного постоянного target после
исчерпания плановой потребности.

## Что считается покрытием полки

Для нужной даты учитываются только количества, которые физически или
подтверждённо окажутся на полке вовремя:

```text
shelf_projected_qty =
    физический остаток полки
    + подтверждённые поступления на полку до нужной даты
    - более ранний расход барабана
```

Количество на другом складе не считается полкой. Оно может породить действие
перемещения, но не новый производственный спрос.

Заказ без подтверждённого склада назначения и срока не считается покрытием
полки.

## Вытягивание мехцеха

Для каждой производимой детали:

```text
shelf_gap_qty =
    max(shelf_target_qty - shelf_projected_qty, 0)

confirmed_open_production_qty =
    незакрытое количество исполнительных строк этого требования
    с подтверждённым сроком и складом назначения

unlaunched_mrp_qty =
    max(
        replenishment_required_qty
        - replenishment_received_qty
        - confirmed_open_production_qty,
        0,
    )

pull_qty =
    min(
        max(shelf_gap_qty - eligible_transfer_qty, 0),
        unlaunched_mrp_qty,
    )

materialized_qty =
    min(round_up(pull_qty, batch_multiple), unlaunched_mrp_qty)
```

Кратность партии применяется только внутри `unlaunched_mrp_qty`.
`materialized_qty` может кратковременно превысить цель полки, но не может
создать выпуск сверх общей незакрытой MRP-потребности.

Физический остаток вне полки сам по себе вытягивание не уменьшает. Учитывается
только свободное количество после удержаний старших резервов, уже адресно
назначенное сохранённому перемещению этого требования:

```text
eligible_transfer_qty =
    min(saved_addressed_transfer_qty, free_other_warehouse_qty)
```

Неназначенный или удержанный остаток другого склада производство не блокирует.
Если количество уже производится с подходящим сроком и назначением, новый
заказ не создаётся.

## Приоритет

Приоритет определяется риском остановки сборки, а не размером общего
дефицита:

1. ближайшая дата нехватки на полке;
2. старшинство потребляющего плана;
3. глубина проникновения в защитное окно;
4. длительность производства;
5. стабильный идентификатор требования.

Практическая величина:

```text
latest_start_date =
    first_shortage_date - ShelfPolicy.replenishment_time_days
```

Чем меньше запас времени до `latest_start_date`, тем выше строка мехцеха.

Мастер получает один список:

- что произвести;
- сколько произвести сейчас;
- к какой дате;
- на какую полку положить;
- какие планы и плитки сборки это защищает;
- что произойдёт со сборкой при задержке.

## Выполнение

Запуск заказа меняет состояние работы, но не выполнение MRP.

Только физический выпуск:

- увеличивает количество на полке;
- адресно-FIFO алгоритм покрывает потребность пополнения;
- уменьшает `replenishment_remaining_qty`.

После сдвига барабана меняются target, срок и приоритет, но не исходное
количество MRP.

## Инварианты

1. Суммарный выпуск задаёт только MRP.
2. Буфер не создаёт отдельный резерв.
3. Target полки не превышает незакрытую потребность живых планов.
4. DBR использует сохранённые нормы происхождения, а не повторный BOM-взрыв.
5. Открытое производство вычитается перед новым вытягиванием.
6. Остаток другого склада приводит к перемещению, а не к дублю производства.
7. Сдвиг барабана меняет только время и приоритет.
8. Физическое выполнение остаётся Ledger-only.
9. Локальный срок полки не заменяет срок пополнения MRP из 1С.
