# План перехода на распределение по видам производства (Версия 2)

## 1. Введение

Текущая система распределения деталей по участкам основана на привязке к этапам производства (`production_stages`). Эта задача предполагает переход на новую модель, в которой привязка и все связанные расчеты будут осуществляться на основе видов производства (`Catalog_ВидыПроизводства` из 1С).

Этот документ описывает скорректированный план миграции на основе уточненной информации о структуре данных.

## 2. Анализ текущего состояния (Скорректированный)

### 2.1. Связь данных в 1С

Повторный анализ метаданных OData показал:

*   Существует справочник `Catalog_ВидыПроизводства`.
*   Связь между спецификацией (`Catalog_Спецификации`) и видом производства (`Catalog_ВидыПроизводства`) **прямая**.
*   В сущности `Catalog_Спецификации` есть `NavigationProperty` с именем `ВидПроизводства`, которое напрямую ссылается на `Catalog_ВидыПроизводства`. Это означает, что у спецификации есть поле `ВидПроизводства_Key`.

**Вывод:** Вид производства является атрибутом спецификации, а не номенклатуры.

### 2.2. Текущая логика в приложении

*   **Привязка к участкам:** Осуществляется через таблицу `resource_stages`, которая связывает `production_resources` (участки) и `production_stages` (этапы).
*   **Определение этапа детали:** Логика определения этапа для детали находится в `backend/app/services/stage_logic.py`. Этап определяется на основе этапов его дочерних компонентов в спецификации.
*   **Синхронизация:** Текущие сервисы синхронизации не загружают `Catalog_ВидыПроизводства`.

## 3. План миграции (Скорректированный)

### Шаг 1: Расширение схемы БД

1.  **Таблица `production_kinds`:** (Без изменений) Для хранения справочника видов производства.
    ```sql
    CREATE TABLE production_kinds (
      id         SERIAL PRIMARY KEY,
      ref_1c     VARCHAR(255) UNIQUE NOT NULL,
      name       VARCHAR(255) NOT NULL,
      created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
      updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );
    ```

2.  **Таблица `resource_production_kinds`:** (Изменение) Для связи участков и видов производства. Введено глобальное ограничение уникальности по `production_kind_id` (один вид производства может быть назначен только одному участку).
    ```sql
    CREATE TABLE resource_production_kinds (
      id                  SERIAL PRIMARY KEY,
      resource_id         INTEGER NOT NULL,
      production_kind_id  INTEGER NOT NULL,
      created_at          TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
      updated_at          TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
      FOREIGN KEY(resource_id) REFERENCES production_resources(resource_id),
      FOREIGN KEY(production_kind_id) REFERENCES production_kinds(id),
      UNIQUE(resource_id, production_kind_id),
      UNIQUE(production_kind_id)
    );
    ```

3.  **Поле `production_kind_id` в таблице `specifications`:** (Изменение) Поле добавляется в `specifications`, а не в `items`.
    ```sql
    ALTER TABLE specifications ADD COLUMN production_kind_id INTEGER;
    ALTER TABLE specifications ADD CONSTRAINT fk_spec_production_kind FOREIGN KEY (production_kind_id) REFERENCES production_kinds(id);
    ```

4.  Обновить документ `docs/db_schema.md`, добавив описание новых таблиц и полей.

### Шаг 2: Реализация синхронизации

1.  **Синхронизация `Catalog_ВидыПроизводства`:** (Без изменений)
    *   Создать ORM-модель `ProductionKind`, схему Pydantic, сервис `production_kind_sync.py` и эндпоинт для синхронизации.

2.  **Синхронизация вида производства для спецификаций:** (Изменение)
    *   Модифицировать сервис `backend/app/services/specification_sync.py`.
    *   При синхронизации спецификаций извлекать поле `ВидПроизводства_Key`.
    *   Находить `id` соответствующего вида производства в таблице `production_kinds`.
    *   Сохранять `id` в поле `specifications.production_kind_id`.

### Шаг 3: Изменение логики распределения

Логика теперь будет выглядеть так:
**Деталь -> Спецификация по умолчанию -> Вид производства -> Участок**

1.  **Обновить `resource_calculator.py` и `planning_service.py`:**
    *   **Сохранить существующую логику определения этапа:** Логика в `stage_logic.py` и ее вызовы для определения `stage_id` детали должны остаться без изменений. Поле `stage_id` будет по-прежнему вычисляться и сохраняться для аналитических целей.
    *   **Добавить новую логику определения участка:**
        1.  Для каждой детали (item) найти ее "спецификацию по умолчанию" (`default_specifications`).
        2.  Из записи о спецификации в таблице `specifications` получить `production_kind_id`.
        3.  По `production_kind_id` найти связанный участок (`resource_id`), используя данные из таблицы `resource_production_kinds`, которые **заполняются вручную** в интерфейсе "Производственные ресурсы".
    *   **Именно этот, новый, механизм привязки к участку через вид производства будет использоваться для всех расчетов загрузки и планирования.** Старая привязка через `resource_stages` больше не будет использоваться для этих целей.

## 5. Риски и их минимизация

*   **Отсутствие спецификации по умолчанию:** Если у детали нет "спецификации по умолчанию", невозможно будет определить вид производства. Необходимо предусмотреть fallback-логику или механизм оповещения о таких деталях.
*   **Производительность:** Цепочка запросов для определения участка (item -> default_spec -> spec -> production_kind -> resource) может быть медленной. Необходимо оптимизировать запросы с помощью JOIN.
*   **Обратная совместимость:** (Без изменений) Переход следует проводить в отдельной ветке и тщательно тестировать.
