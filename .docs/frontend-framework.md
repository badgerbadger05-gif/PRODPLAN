# Фронтенд-фреймворк PRODPLAN

## Цель

Фронтенд развивается как единый ERP-каркас, а не набор независимых страниц.

«Фреймворк» здесь означает:

- единый типизированный контракт с backend;
- один набор базовых визуальных примитивов;
- повторно используемые модели таблиц, фильтров, состояний и действий;
- одинаковый жизненный цикл загрузки и мутаций;
- сборку экранов из существующих сущностей.

Это не задача одномоментно переписать весь UI и не повод создать
универсальный компонент на все случаи.

## Главная граница

Frontend **читает, выбирает и отображает**. Backend **считает, агрегирует,
классифицирует и принимает решения**.

Если значение может повлиять на производственное решение или одинаково
должно выглядеть у двух пользователей, оно рассчитывается backend-ом,
сохраняется в read-model и приходит готовым.

Frontend не вычисляет:

- остатки и дефициты;
- проценты и статусы покрытия;
- выполнение и остаток потребности;
- суммы и KPI журналов;
- приоритеты, зоны, риски и сроки запуска;
- доступность действия;
- группировки производственных потребностей;
- итоги MRP, мощности, полок и барабана.

Запрет действует даже для «простой формулы в одну строку». Простота формулы
не делает frontend её владельцем.

## Одна сущность — одно представление

Фронтенд следует доменной модели backend:

- периодный план существует один раз;
- очередь сборки существует один раз;
- производственный журнал существует один раз;
- закупочный журнал существует один раз;
- карточка номенклатуры существует один раз.

Разные рабочие места являются фильтрами, режимами и проекциями этих
представлений, а не отдельными frontend-сущностями.

DBR не получает собственные копии плана, производственного журнала и
закупочного журнала. Он добавляет барабан, сроки, приоритеты и состояние
полок в существующие экраны.

## Слои

### Транспортный контракт

OpenAPI backend является единственным источником DTO запросов и ответов.
Типы генерируются и не переписываются вручную в `domain`.

Ручной тип допустим только для:

- чистого UI-состояния;
- вычисляемой view-model;
- композиции нескольких сгенерированных DTO.

`api<T>()` с произвольно объявленным `T` не доказывает форму ответа.
Новые endpoint-обёртки должны использовать сгенерированный тип операции.

### Domain

`src/domain` содержит:

- точные алиасы доменных состояний;
- чистые функции форматирования и отображения готовых backend-статусов;
- view-model, которая явно ссылается на транспортные DTO.

Запрещены:

- дублирование полного backend DTO;
- расширение закрытого enum через `| string`;
- `any`;
- `Record<string, unknown>` вместо известного контракта;
- одинаковые типы номенклатуры, склада, статуса и количества в нескольких
  доменных файлах.

Неизвестное значение принимается как `unknown` только на реальной внешней
границе и разбирается одним типизированным адаптером.

### Services

`src/services` — единственное место HTTP-вызовов приложения.

Сервис:

- принимает типизированные параметры;
- строит URL и request DTO;
- вызывает общий транспорт;
- возвращает типизированный response DTO;
- не форматирует данные для экрана;
- не содержит бизнес-математику.

Страницы и компоненты не вызывают `fetch` или `api` напрямую.

### UI

Страница связывает маршрут, загрузку, состояние выбора и готовые компоненты.
Она не владеет транспортными DTO, формулами выполнения или копиями таблиц.

Допустимы только представительные операции:

- локальное форматирование даты и числа;
- выбор CSS-класса по готовому backend-статусу;
- управление формой до отправки;
- вычисление номера видимой строки и состояния кнопок пагинации;
- геометрическая раскладка уже готовой ограниченной read-model.

Клиентская фильтрация и сортировка допустимы только для небольшого
справочника, уже целиком загруженного для формы. Журналы, планы, барабан и
Ledger фильтруются, сортируются, группируются и пагинируются backend-ом.

## Существующий каркас

Расширяются, а не дублируются:

- `DocumentWindow` — оболочка рабочего документа;
- `StatusBar` — состояние приложения;
- `tableDoctype` — описание колонок, сортировки и ширины;
- общие форматтеры `lib/format`;
- общий транспорт `lib/api`;
- существующие предметные picker/dialog/table-компоненты после обобщения
  подтверждённого второго использования.

Если новый экран почти повторяет существующий, сначала расширяется
существующий компонент режимом или колонками.

## Базовые примитивы

Каркас последовательно собирается из небольших типизированных примитивов:

- `DocumentWindow`;
- `EntityTable<TItem, TSortKey>`;
- `FilterBar<TFilters>`;
- `AsyncState` для loading/empty/error/unavailable/stale;
- `TruthBadge` для generation/cutoff/status;
- `ActionDialog<TInput, TResult>`;
- `ItemPicker`, `WarehousePicker`, `DateRange`;
- `QuantityCell`, `StatusCell`, `DeadlineCell`;
- пагинация, сортировка и сохранение фильтров в URL.

Примитив извлекается после появления второго реального использования.
Одинаковая разметка не копируется третий раз.

Примитив не должен знать предметную сущность, если она не нужна его
поведению. Предметные правила остаются в feature-композиции.

## Таблицы и журналы

Описание колонок типизировано ключами строки:

```text
TableColumn<TItem, TKey extends keyof TItem>
```

Колонка определяет заголовок, значение, форматирование, сортировку и ширину в
одном месте. Отдельные массивы колонок для похожих экранов собираются из
общих колонок.

Производственный журнал получает дополнительные DBR-колонки:

- крайний срок запуска;
- целевая полка;
- текущая величина вытягивания;
- защищаемые плитки;
- риск остановки сборки.

Отдельная «очередь мехцеха DBR» не создаётся.

Закупочный журнал аналогично расширяется проекциями резерва, не получает
отдельный DBR-журнал.

Каждый backend-ответ журнала содержит готовые:

```text
rows
page
page_size
total_rows
summary
available_actions
```

Строка содержит готовые `remaining_qty`, `execution_pct`, `status`,
`status_label`, `priority`, `deadline` и флаги допустимых действий. Frontend
не восстанавливает их из базовых полей.

Для барабана backend возвращает готовые дни, дорожки, плитки, разрывы и KPI.
Для полок — готовые target, projected, gap, pull, first_shortage и priority.
Для MRP — готовые итоги каждого потока и мощности.

## Состояние истины

Каждая read-model, содержащая расчётные или физические значения, несёт:

```text
ledger_generation
cutoff
truth_status
unavailable_reason
```

Общий `AsyncState` различает:

- загрузку;
- пустой достоверный результат;
- ошибку;
- `unavailable`;
- `stale`.

Ноль не используется вместо неизвестного значения. Компоненты не
пересчитывают backend-показатели.

## Состояние и навигация

- серверный снимок не копируется в несколько локальных хранилищ;
- фильтры, сортировка, страница и выбранный документ отражаются в URL;
- после мутации перечитывается канонический backend-ответ;
- оптимистичное изменение допустимо только для локального UI-состояния;
- открытие страницы не запускает тяжёлый расчёт.
- страница не строит вторичную расчётную read-model через `reduce`, `groupBy`
  или арифметику над строками ответа.

Новая библиотека управления состоянием не добавляется, пока React и URL
достаточны.

## Эволюционное внедрение

Большого переписывания нет. При работе над экраном выполняется правило:

1. использовать существующую доменную сущность и сервис;
2. заменить ручной DTO сгенерированным типом затронутого endpoint;
3. добавить в backend read-model недостающие готовые значения;
4. удалить соответствующую формулу или агрегацию из frontend;
5. убрать прямой HTTP-вызов из страницы;
6. переиспользовать существующий примитив;
7. извлечь новый примитив только при подтверждённом повторении;
8. удалить заменённую копию в той же волне;
9. добавить focused test backend-контракта и его отображения.

Не затронутые экраны мигрируют следующими небольшими волнами.

## Проверки

Обязательные frontend-гейты:

```text
OpenAPI generation + no diff
TypeScript build
ESLint
Vitest
bundle check
Playwright smoke
```

Статическая проверка должна запрещать:

- прямой `fetch`/`api` из `ui`;
- новые `any`;
- ручное дублирование сгенерированных DTO;
- новые открытые enum `Known | string`;
- предметные `reduce`, вычисление процентов, остатков, дефицитов и статусов
  внутри `ui` и `domain`;
- третью копию таблицы, диалога или picker без общего примитива.

## Приёмка

Изменение UI принимается, если:

1. не создана новая копия существующей сущности;
2. транспорт типизирован от OpenAPI;
3. бизнес-формула не перенесена во frontend;
4. все итоги, статусы и доступные действия пришли из сохранённой read-model;
5. использован общий каркас;
6. заменённый код удалён;
7. все frontend-гейты зелёные.
