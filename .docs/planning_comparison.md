# Параллельное сравнение планирования

Новый контур хранит результаты сравнений в собственной shadow-БД. Стабильный
PRODPLAN никогда не подключается к этой БД: его состояние читается только через
HTTP API, заданный `STABLE_PRODPLAN_API_URL`.

## API

- `GET /api/v1/planning-comparison/input-fingerprint` — read-only отпечаток
  входных watermark и последнего прогона. `include_results=true` добавляет
  канонические результаты последнего прогона.
- `POST /api/v1/planning-comparison/captures` — ручной снимок. Он читает у
  стабильного контура sync status, последний run, summary и канонический
  snapshot; локально только читает последний готовый run. Планирование и запись
  в 1С этот endpoint не запускает.
- `GET /api/v1/planning-comparison/batches` и `/batches/{id}` — история и diff.

`capture_key` идемпотентен: повторный запрос возвращает уже сохранённый batch.
Ключ непустой и ограничен 128 символами; `max_skew_seconds` допускается от 0
до 86400 секунд.

Fingerprint включает отдельные канонические hash/count для строк периодного
плана, default-спецификаций и BOM, операций/маршрутов, ресурсов и мощностей,
рабочего календаря, настроек планирования и выбора складов. Оценка `exact`
возможна только при совпадении всех этих компонент.

Межэкземплярные origin-маркеры не содержат локальных идентификаторов БД.
У старых `planned_purchase` пока нет устойчивого UUID дельты: две действительно
разные дельты с полностью одинаковыми поставщиком, строками, датами и
количеством неразличимы. До добавления durable delta key это явно ограничивает
защиту, а не заменяется небезопасным локальным id.
Batch, события, сырые snapshot, нормализованные строки и diff являются
append-only; API изменения и удаления не предоставляет.

## Сопоставимость срезов

- `exact`: совпал полный input fingerprint;
- `near`: периоды совпали, а расхождение всех доступных watermark не превышает
  `max_skew_seconds` (по умолчанию 300);
- `invalid`: отсутствует watermark, различаются периоды или превышен допуск.

Даже `invalid` сохраняется как доказательный снимок, но его нельзя использовать
для оценки качества алгоритма как сравнение одинаковых входов.

### Совместимость с текущим стабильным PRODPLAN

Стабильный сервер можно оставить без обновления. Capture сначала пробует новый
`input-fingerprint`, а при ответе `404` переходит на его существующие read-only
endpoint'ы:

- `/sync/auto/status`;
- `/plan/runs`;
- постраничные `/plan/results/{run_id}/production`, `/purchases`, `/rework`.

Исходные ответы и каждая страница сохраняются в snapshot
`legacy_result_pages`, после чего строки нормализуются по GUID 1С или
бизнес-коду. Так как старые result DTO содержат только локальный `item_id`,
capture дополнительно читает существующий `GET /items/{item_id}` и сохраняет
полученные карточки в том же сыром snapshot. Сам локальный ID между двумя
независимыми БД никогда не используется как ключ.
Legacy-срез никогда не получает оценку `exact`, поскольку старый API не может
доказать тождество всех входов. Возможны только:

- `near`, если периоды совпадают и доступные watermark синхронизации укладываются
  в допуск;
- `invalid` с явной причиной при отсутствии watermark, разных периодах или
  слишком большом временном сдвиге.

Для защиты от бесконечной/ошибочной пагинации используются ограничения
`PLANNING_COMPARISON_PAGE_SIZE` (по умолчанию 100, максимум 5000) и
`PLANNING_COMPARISON_MAX_PAGES` (по умолчанию 100, максимум 1000). HTTP timeout
применяется к каждой странице. Число карточек ограничивает
`PLANNING_COMPARISON_MAX_ITEM_LOOKUPS` (по умолчанию 10000).

## Ключи и числа

Строки сопоставляются по `item_ref1c`, с fallback на `item_code`; для закупок в
ключ входит `supplier_ref1c`, для переработки — `spec_ref1c`/`spec_code`, а также
дата корзины. Локальные числовые ID в ключи не входят. Количества проходят через
`Decimal` и хранятся как `DECIMAL(24,6)`. Каждый сырой payload имеет SHA-256.

Дополнительные переменные:

- `STABLE_PRODPLAN_API_TOKEN` — необязательный Bearer token;
- `PLANNING_COMPARISON_HTTP_TIMEOUT` — timeout чтения, по умолчанию 20 секунд.
- `PLANNING_COMPARISON_PAGE_SIZE` — размер страницы legacy API;
- `PLANNING_COMPARISON_MAX_PAGES` — предельное число страниц на один вид результата.
- `PLANNING_COMPARISON_MAX_ITEM_LOOKUPS` — предел карточек номенклатуры legacy API.

Планировщик захвата намеренно пока не добавлен: первый этап запускается вручную,
чтобы проверить нагрузку и качество cutoff на реальном сервере.
