# Миграция фронта в ERP-shell

## Решение

Новый целевой интерфейс PRODPLAN делаем как отдельный React ERP-shell: плотный рабочий интерфейс в стиле производственной ERP, без Quasar и без Frappe/ERPNext.

Quasar-фронт пока остается рабочим источником поведения и паритета. Переносим не "все подряд", а только реальные экраны с подтвержденной логикой, API и пользовательской ценностью.

## Что переносим

| Экран | Старый маршрут | Статус переноса |
| --- | --- | --- |
| Журнал заказов | `/production-control` | Первый экран-прототип в `frontend-erp-shell` |
| MRP прогоны | `/mrp` | Переносить после каркаса shell |
| Результат MRP | `/mrp/:runId` | Переносить с ревизией таблиц и вкладок |
| План выпуска квартальный | `/plan/quarterly` | Переносить как плотную табличную форму |
| Отчет о выпуске недельный | `/plan/production-report/week` | Переносить 1-в-1 по подтвержденной логике |
| Синхронизация 1С | `/sync` | Переносить с группировкой действий и единой индикацией прогресса |
| Производственные ресурсы | `/resources` | Переносить после проверки реального использования |
| Распределение этапов | `/stages` | Переносить после проверки сценария |
| Спецификации | `/specification` | Переносить как диагностический/рабочий экран |
| Главная | `/` | Делать только полезную стартовую страницу, без декоративных заглушек |

## Что не переносим

- Неиспользуемые страницы без маршрута, например старый `PlanPage.vue`.
- Старые настройки без маршрута, например `SettingsPage.vue`, пока нет подтвержденного сценария.
- Заглушки, декоративные уведомления, колокольчики, пустые отчеты.
- Удаленные ранее пункты меню: дневной план, расчет заказов, мертвые настройки и отчеты.
- GUID как основной текст в интерфейсе. GUID допустим только в диагностике, если рядом есть человекочитаемое имя.

## Правила интерфейса

1. Интерфейс плотный: рабочая ERP-форма, таблицы, командные панели, статусная строка.
2. Палитра: графит, серый, золото; без мультяшности и без лишних карточек.
3. Таблицы являются главным элементом интерфейса, а не вторичным блоком.
4. Наименование и артикул по возможности показываются вместе, если так быстрее читать.
5. Кнопки только рабочие. Если действие не реализовано, кнопки быть не должно.
6. Фронт не дублирует бизнес-логику MRP, а показывает данные backend API.
7. Для каждого экрана перед переносом делается мини-ревизия: маршрут, API, сценарий, мертвые элементы, обязательные проверки.

## Технический план

1. Зафиксировать `frontend-erp-shell` как новый фронтенд-контур рядом со старым `frontend`.
2. Разобрать прототип на основу:
   - `AppShell`;
   - `WindowFrame`;
   - `CommandBar`;
   - `FilterBar`;
   - `DataGrid`;
   - `DetailPane`;
   - `StatusBar`;
   - `api` client.
3. Первым довести до рабочего паритета журнал заказов.
4. Затем перенести MRP: список прогонов и результат прогона.
5. После этого переносить план выпуска, недельный отчет и синхронизацию.
6. Старый Quasar удалять только после прохождения паритета по всем живым экранам.

## Проверка каждого перенесенного экрана

- `npm run build` в новом фронте.
- Проверка реального API, а не моков.
- Нет мертвых кнопок.
- Нет несуществующих пунктов меню.
- Таблица читается в плотном рабочем режиме.
- Пользовательский сценарий короче или не хуже старого.
