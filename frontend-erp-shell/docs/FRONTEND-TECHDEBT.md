# Технический долг фронтенда

Статус: РЕЕСТР. Приоритеты P0 (несущее) → P3 (косметика). Обновлять по мере закрытия.

## P0 — Doctype-framework (главная боль)

**Проблема.** Каждая страница пишется с нуля: своё состояние, загрузка, вёрстка, мапы лейблов, действия. `tableDoctype` описывает только колонки. Итог — каждый экран **разный**, ~200 строк однотипной механики дублируются на каждой странице, поведение (пагинация/сортировка/ошибки/хоткеи) расходится, тестировать нечего.

**Влияние.** Скорость и стоимость каждой новой страницы; несогласованный UX; невозможность добавлять «карточки элементов» ledger-проекта единообразно.

**Цель.** Единый нормативный контракт страниц — см. **`DOCTYPE.md`**: Doctype = декларативное описание целой страницы (meta/columns/filters/actions/detail/permissions), рантайм `useDoctypeList` + `DoctypePage` + общие `CommandBar/FilterBar/DoctypeTable/FormRenderer/DialogHost`. Новый экран = один Doctype-объект + сервис. Внедрять инкрементально поверх существующего `tableDoctype` (дорожная карта §8 в DOCTYPE.md).

**Где.** `src/ui/doctype/` (новый рантайм), `src/ui/pages/*` (миграция по одной).

## P0/P1 — Авторизация и роли (СЕЙЧАС ОТСУТСТВУЮТ ПОЛНОСТЬЮ)

**Проблема.** На фронте **нет аутентификации и авторизации**: в `src/lib/api.ts` нет заголовка `Authorization`/токена/`credentials`; нет логина, сессии, понятия текущего пользователя и ролей. **Любой, кто открыл приложение, видит все экраны и может нажать любое действие**, включая проведение документов в 1С (СборкаЗапасов, ПеремещениеЗапасов, СдельныйНаряд) и экспорт заказов.

**Влияние.** Безопасность (неконтролируемый доступ к записи в 1С), и продуктовый разрыв (кладовщик/закупщик/планировщик/админ должны видеть разное).

**Цель.**
1. **Аутентификация:** бэкенд выдаёт сессию/токен; `api.ts` шлёт его в каждом запросе; 401 → редирект на логин. Единая точка — HTTP-клиент (не по страницам).
2. **Роли (RBAC):** роль(и) пользователя приходят с бэкенда; фронт гейтит **экраны** (роутинг/навигация) и **действия** через `Doctype.permissions` (`view: Role[]`, `actions: Record<key, Role[]>` — уже заложено в схеме Doctype). Кнопка недоступной роли — скрыта/заблокирована, а не только спрятана в UI: **бэкенд обязан проверять права независимо** (фронт-гейт — UX, не безопасность).
3. **Минимальный набор ролей** (уточнить с владельцем): admin, планировщик, закупщик, кладовщик (цех), наблюдатель. Особо — право «проведение в 1С» и «экспорт в 1С» как отдельные разрешения (это запись в источник правды).

**Где.** `src/lib/api.ts` (токен/401), `src/ui/App.tsx` (роутинг-гейт), `Doctype.permissions`, + бэкенд (эндпоинты `me`/`login`, серверная проверка прав).

## P1 — Тестовое покрытие ≈ 0

**Проблема.** Есть один Playwright-smoke + характеристические тесты только на 2 god-компонента (добавлены недавно). Остальное не покрыто; регрессию поймать нечем.

**Цель.** На каждый Doctype — характеристический vitest-тест (рендер + 1–2 флоу, мок сервисов), по образцу `ProductionControlPage.test.tsx`. Прогон в CI (см. P3). `useDoctypeList`/`DoctypePage` покрыть юнит-тестами один раз — это защитит все страницы разом.

## P1 — God-компоненты

**Проблема.** `PeriodPlanPage` (1721 стр.), `ProductionControlPage` (1303 стр.) — частично распилены на ветке рефакторинга, но остаются крупными; вся стейт-логика в одном файле.

**Цель.** Финальная декомпозиция через Doctype: страница → тонкая обёртка над `DoctypePage`, стейт → `useDoctypeList`, диалоги → `DialogHost`. Непокрытые тестами интрикейт-флоу (produce-submit, chain-close, редактирование матрицы) — сперва покрыть, потом дробить.

## P2 — Нет UI-кита и дизайн-токенов

**Проблема.** Вся вёрстка на голых `div`/`table` + один `src/styles.css`; нет компонентов (кнопка/селект/бейдж/диалог/таблица), нет токенов (цвета/отступы/типографика), нет темизации. Отсюда визуальный разнобой между экранами.

**Цель.** Минимальный внутренний UI-кит (Button/Select/Badge/Dialog/Table-ячейки) + токены; либо headless-библиотека без тяжёлого фреймворка. Doctype-рантайм рендерит через этот кит — единый вид «бесплатно». Не тащить тяжёлый UI-фреймворк без нужды.

## P2 — Протечки прямых `api()`/`fetch` мимо сервисов

**Проблема.** Часть страниц ходит в API напрямую из компонента (исторически `ProductionControlPage` — 30 инлайновых вызовов + сырой `fetch`; вынесено в `services/productionControl.ts` на ветке рефакторинга; `TransferRequestsPage` и др. ещё содержат инлайновые вызовы).

**Цель.** Правило Doctype: данные только через `src/services/*`. Дочистить оставшиеся инлайновые вызовы; закрепить lint-правилом/ревью.

## P2 — Типизация границы API (`any`)

**Проблема.** eslint показывает ошибки `@typescript-eslint/no-explicit-any` (напр. `chainPreview`, piecework-cast). Граница API типизирована не до конца.

**Цель.** Типизировать ответы сервисов в `domain/*`; убрать `any`; включить правило в CI.

## P2 — Копипаст-архитектура journal'ов

**Проблема.** `production-control/` и `purchase-control/` построены «под копирку» (5 почти одинаковых по структуре файлов) — параллельная кодовая база.

**Цель.** Обобщить в один generic-журнал на базе Doctype (это ровно то, что даёт Doctype-framework). Делать после стабилизации рантайма — поведенческий мёрж, нужны тесты.

## P3 — Нет CI по фронту

**Проблема.** CI отсутствует (и по бэку тоже — см. общий аудит). `tsc`/`eslint`/`vitest`/`build` не гоняются автоматически.

**Цель.** GitHub Actions: `tsc --noEmit` + `eslint` (0 новых) + `vitest run` + `vite build` на PR. Это же гейт для правил Doctype (запрет инлайновых `api()`, обязательность тестов на Doctype).

## P3 — Прочее

- **i18n:** хардкод русского в компонентах. Приемлемо сейчас; при необходимости — вынести строки. Лейблы enum уже уходят в `Doctype.options`.
- **UX загрузки/ошибок:** разные экраны показывают loading/error по-разному → стандартизируется `useDoctypeList` (единые состояния) + `StatusBar`.
- **Доступность (a11y):** голые таблицы без ролей/навигации с клавиатуры — учесть в `DoctypeTable`.
