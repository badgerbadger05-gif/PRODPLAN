# Выгрузка PRODPLAN в 1С

Статус: рабочий документ для доработки PRODPLAN. Дата: 2026-05-19.

Цель: описать, какие документы PRODPLAN должен создавать в 1С, в каком порядке, через какие OData EntitySet и какие документы 1С остаются источником обратной загрузки.

## Главный принцип

PRODPLAN становится операционным контуром планирования и производственного исполнения. 1С остается учетным контуром.

В 1С из PRODPLAN выгружаются только документы намерения и производственно-складские события, которые должны появиться в учете:

1. заказ на производство;
2. перемещение запасов;
3. выпуск/сборка запасов;
4. заказ поставщику.

Приходные накладные, оприходования и списания не создаются из PRODPLAN. Они создаются в 1С и затем импортируются обратно в PRODPLAN/ERPNext-слой как факт прихода или корректировки.

## Матрица направлений

| Процесс | Источник | Приемник | Документ 1С | Направление |
|---|---|---|---|---|
| Заказ на производство | PRODPLAN | 1С | `Document_ЗаказНаПроизводство` | PRODPLAN -> 1С |
| Перемещение между складами | PRODPLAN | 1С | `Document_ПеремещениеЗапасов` | PRODPLAN -> 1С |
| Передача материалов в производство | PRODPLAN | 1С | `Document_ПеремещениеЗапасов` или отдельное правило WIP | PRODPLAN -> 1С |
| Выпуск продукции | PRODPLAN | 1С | `Document_СборкаЗапасов` | PRODPLAN -> 1С |
| Заказ поставщику | PRODPLAN | 1С | `Document_ЗаказПоставщику` | PRODPLAN -> 1С |
| Приход от поставщика | 1С | PRODPLAN | `Document_ПриходнаяНакладная` | 1С -> PRODPLAN |
| Оприходование фактических остатков | 1С | PRODPLAN | `Document_ОприходованиеЗапасов` | 1С -> PRODPLAN |
| Списание фактических остатков | 1С | PRODPLAN | `Document_СписаниеЗапасов` | 1С -> PRODPLAN |
| Сверка остатков | обе системы | отчет | регистры остатков 1С + остатки PRODPLAN | read-only |

## Нумерация документов 1С

Поле `Number` в 1С короткое. Длинный номер вида `ERPNext-TRANSFER-PROBE-0001` был обрезан 1С до `ERPNext-TRA`.

Правило:

- для тестовых документов использовать короткий номер вида `ERPNext0001`;
- для рабочих документов нужен короткий, уникальный, легко узнаваемый префикс, например `PP00000001` или `ERPNext0001`;
- полный исходный ключ PRODPLAN хранить не в `Number`, а в комментарии и таблице связей.

Минимальный маркер в 1С:

```text
Комментарий = PRODPLAN source=<doctype>/<id>; run=<sync_run_id>
```

## Порядок пакетной выгрузки

1. Взять lock обмена, создать `sync_run`.
2. Обновить справочники и маппинги, необходимые для документов: номенклатура, единицы, склады, участки, поставщики.
3. Выгрузить новые и измененные заказы на производство.
4. Выгрузить перемещения запасов.
5. Выгрузить передачу материалов в производство, если принято решение отражать WIP в 1С отдельным перемещением.
6. Выгрузить выпуск/сборку продукции.
7. Выгрузить заказы поставщикам.
8. Импортировать из 1С приходные накладные, созданные на основании выгруженных заказов поставщикам.
9. Импортировать из 1С оприходования и списания по фактическим расхождениям.
10. Выполнить read-only сверку остатков.
11. Обновить курсор каждого этапа только после успешной записи и сохранения внешнего ключа.

Если заказ на производство не выгрузился в 1С, связанные производственные движения не должны уходить в 1С без основания.

## Идемпотентность

Нужна таблица связей, чтобы повторный запуск не создавал дубль.

Минимальные поля `sync_link`:

| Поле | Назначение |
|---|---|
| `source_system` | `PRODPLAN` |
| `source_doctype` | тип исходного документа PRODPLAN |
| `source_id` | внутренний id исходного документа |
| `target_system` | `1C` |
| `target_entity` | OData EntitySet 1С |
| `target_ref_key` | `Ref_Key` документа 1С |
| `target_number` | короткий номер документа 1С |
| `payload_hash` | hash нормализованного payload |
| `status` | `planned`, `success`, `error`, `cancelled` |
| `last_error` | последняя ошибка записи |
| `last_synced_at` | дата последней успешной синхронизации |

Курсор хранить отдельно по каждому этапу, например:

| Этап | Ключ идемпотентности | Курсор |
|---|---|---|
| production_order_export | id заказа PRODPLAN | `updated_at`, `id` |
| stock_transfer_export | id складского события PRODPLAN | `posted_at`, `id` |
| manufacture_export | id события выпуска PRODPLAN | `posted_at`, `id` |
| purchase_order_export | id заказа поставщику PRODPLAN | `updated_at`, `id` |
| purchase_receipt_import | `Ref_Key` 1С | `Date`, `Ref_Key` |
| stock_adjustment_import | `Ref_Key` 1С | `Date`, `Ref_Key` |

## Безопасность записи

Все write-сценарии сначала выполнять только на `unf_demo`.

Защита в коде должна проверять:

1. профиль окружения: `demo`;
2. URL содержит `unf_demo`;
3. явный флаг записи включен;
4. для каждого этапа указан разрешенный `EntitySet`;
5. dry-run не пишет в 1С и не двигает курсоры.

Рабочую базу `unf` подключать только после проверки полного пакета на демо-копии.

## Что не делать

1. Не создавать в 1С приходные накладные из PRODPLAN.
2. Не создавать в 1С оприходования и списания из PRODPLAN.
3. Не выгружать агрегированный остаток как факт движения.
4. Не перезаписывать остатки в PRODPLAN/ERPNext напрямую без складского документа.
5. Не создавать повторный документ в 1С, если уже есть `sync_link` с успешным `Ref_Key`.
6. Не проводить документы автоматически до подтверждения 1С-программистом обязательных реквизитов и правил проведения.

## Открытые решения

1. Какой короткий формат номера использовать в бою: `PP00000001`, `ERPNext0001` или отдельный префикс 1С.
2. Нужно ли отражать WIP-передачу отдельным перемещением в 1С.
3. Какие реквизиты 1С обязательны для проведения каждого типа документа: организация, склад, подразделение, операция, хозяйственная операция, состояние, ответственный.
4. Какой документ PRODPLAN считать источником факта выпуска: существующий производственный факт, новое складское событие или отдельный экспортный документ.
5. Как импортировать корректировки 1С в PRODPLAN: отдельной таблицей движений или через существующую модель остатков.
6. Как обрабатывать отмены, сторно и возвраты поставщику.

## Практический следующий шаг для PRODPLAN

1. Найти в backend текущие модели производственных заказов, поставщиков, складских движений и остатков.
2. Добавить таблицы `sync_run`, `sync_cursor`, `sync_link`.
3. Добавить сервис `one_c_export_service` с режимами `dry_run` и `apply`.
4. Начать с одного этапа: `Document_ЗаказНаПроизводство`.
5. После успешного dry-run и demo apply добавить перемещение, сборку и заказ поставщику.
