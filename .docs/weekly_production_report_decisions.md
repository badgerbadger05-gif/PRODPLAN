# Решения по задаче: «Отчёт о выпуске техники (недельный)»

Дата: 2026-01-28

## 1) Контекст текущего обсуждения

Проблема: если план по выпуску корневого изделия не выполнен в срок, то из‑за сдвига плана «влево» потребность в MRP может исчезать. Требуется механизм отслеживания факта выполнения плана по технике, чтобы:

- видеть выполнение по дням недели;
- видеть «остаток к выпуску» за неделю;
- переносить невыполненный остаток на следующую неделю.

Текущее состояние проекта:

- Существует страница «План выпуска техники дневной» ([`PlanPage.vue`](frontend/src/pages/PlanPage.vue:1)), работающая как матрица «изделия × даты», построенная на таблице плана [`ProductionPlanEntry`](backend/app/models.py:293) через API `/v1/plan/matrix` ([`get_plan_matrix()`](backend/app/routers/plan.py:119)) и сервис [`query_plan_matrix_paginated()`](backend/app/services/plan_service.py:21).
- План хранится в `production_plan_entries` (поля: `planned_qty`, `completed_qty`, `status`, `notes`) ([`ProductionPlanEntry`](backend/app/models.py:293)).

## 2) Обсуждаемая задача (целевой функционал)

Вместо «План выпуска техники дневной» сделать таблицу/страницу: **«Отчёт о выпуске техники недельный»**.

UI (логика на уровне требований):

- В строках: техника (изделия), у которых **есть ненулевые количества** в текущей неделе плана.
- В столбцах:
  1) Дни недели (7 колонок) — **пустые редактируемые ячейки** (факт выпуска по дням).
  2) 8‑й столбец — **план на текущую неделю** (фиксированное значение).
  3) 9‑й столбец — **остаток** = `план недели - сумма введённого факта по дням`.
- Кнопка сверху: **«Сохранить изменения»**.

Правило переноса:

- После окончания недели остаток (если `остаток > 0`) переносится на **следующую неделю**, на **среду**.
- Выбран режим переноса: **вручную** — кнопка **«Закрыть неделю и перенести остатки»** (с подтверждением).
- Дополнение: при закрытии недели нужно **сформировать “новую таблицу/снапшот” плана текущей недели на момент закрытия** (чтобы “план недели” не плавал при дальнейших пересчётах/правках).

## 3) Ключевые риски (кратко)

Полный разбор рисков в ходе обсуждения (основные источники проблем):

1) Граница недели/часовой пояс и типы дат (`DateTime` в плане) → риск пропуска/двойного учёта строк.
2) «Снапшот плана» vs «живой план» → риск плавающего плана и некорректного остатка.
3) Идемпотентность закрытия недели → риск двойного переноса (двойной клик/таймаут/параллельные пользователи).
4) Конфликт переноса со следующей неделей (на среде уже есть план/факт) → риск потери/удвоения.
5) Негативный остаток и перевыпуск → риск некорректных значений и спорных правил.

## 5) Примечания по реализации (для инженера)

Этот раздел — подсказки для реализации после того, как вы заполните ответы выше:

- План сейчас хранится как `DateTime`, а выборки в сервисе строятся интервалами `>= start` и `< end` ([`query_plan_matrix_paginated()`](backend/app/services/plan_service.py:21)) — при недельном отчёте лучше нормализовать плановые даты к `YYYY-MM-DD` и хранить/сравнивать как `Date` (или строго как полуночь).
- Закрытие недели должно быть транзакционным и идемпотентным (уникальный ключ недели).
- Снапшот плана должен быть независим от дальнейших правок `production_plan_entries`, иначе “план недели” будет плавать.
