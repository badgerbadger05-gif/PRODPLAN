## Расценка через OData: выводы 2026-06-24

Проблема: в документах `Document_СдельныйНаряд`, созданных PRODPLAN с номерами
`PW*`, поле строки `Операции.Расценка` может оставаться пустым/нулевым, хотя в
карточке операции 1С видна цена, например `10,00`.

Проверенный пример из боевой базы:

- `Document_СдельныйНаряд` `PW001309087`, `Ref_Key=9defacb4-6eeb-11f1-934d-9ee51454587f`.
- Строка операции:
  - `Операция_Key=2ef67ffc-aca7-11ef-91bb-9ee51454587f`
    (`Кронштейн задней подвески, гибка`);
  - `Номенклатура_Key=89a4f566-a183-11ef-941f-9ee51454587f`
    (`Кронштейн задней подвески левый, 3мм, Л+Г`);
  - `НормаВремени=0.004`;
  - `Расценка=0`, `Стоимость=0`.
- В локальной БД PRODPLAN для той же операции:
  - `operations.operation_id=643`;
  - `operations.operation_price=0.00`.
- В штатных документах 1С по той же паре `Операция_Key + Номенклатура_Key`
  найдены строки с ненулевой расценкой:
  - `ЗСНФ-002917` от `2026-05-20`: `НормаВремени=0.004`, `Расценка=10`;
  - `ЗСНФ-000880` от `2026-02-10`: `НормаВремени=0.004`, `Расценка=10`;
  - `ЗСНФ-000618` от `2026-01-30`: `НормаВремени=0.004`, `Расценка=10`.
- В старых штатных документах 2025 года по тем же ключам также встречается
  `Расценка=5`, поэтому использовать произвольную историческую строку нельзя.

Обновление 2026-06-26: после включения автоматического REST-интерфейса в 1С в
`$metadata` появился регистр `InformationRegister_ЦеныНоменклатуры`. Цена
операции `10,00` подтверждена прямым запросом к нему:

- entity: `InformationRegister_ЦеныНоменклатуры`;
- метод: `SliceLast(Period=datetime'<дата документа>')`;
- фильтр:
  `Номенклатура_Key eq guid'<Операция_Key>' and ВидЦен_Key eq guid'<ВидЦен_Key>'`;
- для операции `2ef67ffc-aca7-11ef-91bb-9ee51454587f` и вида цены
  `81c4a02c-991b-11eb-e39a-fa163e61326a` возвращается `Цена=10`;
- для изделия `89a4f566-a183-11ef-941f-9ee51454587f` тот же вид цены возвращает
  другую цену (`116`), поэтому расценку сдельного наряда надо искать именно по
  `Операция_Key`, а не по `Номенклатура_Key` изделия.

Рабочее правило PRODPLAN:

1. При формировании строк сдельного наряда использовать дату документа и вид
   цены документа. Сейчас основной вид цены - `Учетная цена`,
   `81c4a02c-991b-11eb-e39a-fa163e61326a`; его можно переопределить в OData
   config через `piecework_price_type_ref1c`,
   `default_piecework_price_type_ref1c` или
   `default_accounting_price_type_ref1c`.
2. До записи/проведения документа вызвать
   `InformationRegister_ЦеныНоменклатуры/SliceLast(...)` по каждой
   `Операция_Key`.
3. Если регистр вернул положительную `Цена`, явно записать в строку
   `Операции.Расценка` и `Операции.Стоимость = КоличествоФакт * Цена`.
4. В шапку документа явно записывать `ВидЦен_Key`.
5. Если цена из регистра не найдена, оставить локальную цену строки, если она
   уже была больше нуля. Исторические строки штатных `ЗСНФ*` по
   `Операция_Key + Номенклатура_Key` можно использовать только как аварийный
   фолбэк и только с проверкой даты/вида цены, потому что по тем же ключам
   встречались разные цены (`10` и `5`).
6. Рассчитывать, что 1С сама заполнит `Расценка` при OData-записи или `Post`,
   не следует: на примере `PW001309087` проведение не заполнило нулевую
   расценку.

## СоставБригады

Поля:

- `LineNumber`
- `Сотрудник_Key`
- `КТУ`
- `СтруктурнаяЕдиница_Key`
- `КлючСвязи`

Связи:

- `Сотрудник_Key` -> `Catalog_Сотрудники`
- `СтруктурнаяЕдиница_Key` -> `Catalog_СтруктурныеЕдиницы`

Для связи строки операции и строк бригады используется одинаковый `КлючСвязи`.

Перед созданием сдельных нарядов PRODPLAN должен синхронизировать `Catalog_Сотрудники` через `POST /api/v1/sync/employees-odata`. В локальной БД хранится `employees.employee_ref1c`.

В 1С есть два режима заполнения исполнителя:

- один исполнитель на все операции: заполняется шапка `Исполнитель`, строки `Операции.Исполнитель` не заполняются;
- разные исполнители по операциям: шапка `Исполнитель` не заполняется, исполнитель указывается в каждой строке `Операции`.

Режим фиксируется реквизитом `ПоложениеИсполнителя`: `ВШапке` или `ВТабличнойЧасти`. Текущий поток PRODPLAN "Произвести" выбирает исполнителя по каждой операции, поэтому использует второй режим и отправляет `ПоложениеИсполнителя=ВТабличнойЧасти`. `СоставБригады.Сотрудник_Key` используется для состава бригады.

## Правило Основания

Для нашего контура важна не только прямая ссылка, а создание документов “на основании”:

- `Document_ПеремещениеЗапасов` -> `ДокументОснование=<Ref_Key заказа на производство>`, `ДокументОснование_Type=StandardODATA.Document_ЗаказНаПроизводство`.
- `Document_СборкаЗапасов` -> только
  `ЗаказНаПроизводство_Key=<Ref_Key заказа на производство>`; generic
  `ДокументОснование`/`_Type` не отправляются, потому что живая метадата 1С не
  допускает в этом составном поле `Document_ЗаказНаПроизводство`.
- `Document_СдельныйНаряд` -> `ДокументОснование=<Ref_Key сборки/производства>`, `ДокументОснование_Type=StandardODATA.Document_СборкаЗапасов`.

На демо-базе у существующих сдельных нарядов `ЗСНФ-*` поле основания заполнено именно ссылкой на `Document_СборкаЗапасов`. Без этих двух полей в интерфейсе список показывает пустую колонку `Основание`, как у первых probe-документов `PW25052501` и `PW25052502`.

## Probe

```powershell
$env:ODATA_BASE_URL="http://mtzw7/unf_demo/odata/standard.odata"
$env:ODATA_USERNAME="<user>"
$env:ODATA_PASSWORD="<password>"
python tools/diagnostics/piecework_order_probe.py --read
```

Проверка payload без записи:

```powershell
python tools/diagnostics/piecework_order_probe.py `
  --number PW00000001 `
  --order-ref "<production-order-ref>" `
  --basis-ref "<manufacture-ref>" `
  --item-ref "<item-ref>" `
  --operation-ref "<operation-ref>" `
  --employee-ref "<employee-ref>"
```

Запись в тестовую базу:

```powershell
python tools/diagnostics/piecework_order_probe.py `
  --apply `
  --number PW00000001 `
  --order-ref "<production-order-ref>" `
  --item-ref "<item-ref>" `
  --operation-ref "<operation-ref>" `
  --employee-ref "<employee-ref>"
```

Скрипт откажется писать, если URL не содержит `unf_demo`.
