# Архитектура PRODPLAN

## Граница систем

1С создаёт физические документы и движения. PRODPLAN зеркалит их в Item
Ledger, создаёт планы и управляет предложениями производства и закупки.

Резервы существуют только в PRODPLAN. В 1С вручную экспортируются
исполнительные документы, но их количество и статус не считаются физическим
фактом.

## Поток данных

```text
периодный план
    │ фиксация один раз
    ├── верхнеуровневый выпуск ──> общая очередь сборки ──> барабан
    │
    └── BOM-развёртка ──> полные резервы ──> потребности пополнения
                                                │
                              ┌─────────────────┴────────────────┐
                              │                                  │
                         make │                                  │ buy
                              v                                  v
                    журнал производства                 журнал закупки
                              │                                  │
                              └──────── физические факты ────────┘
                                                │
                                                v
                              Item Ledger + адресность/FIFO резервов
```

## Периодный план

План редактируется только в `draft`. Фиксация атомарно создаёт один
неизменяемый снимок выпуска, BOM, резервов и потребностей пополнения.

Повторного MRP-прогона, ре-аллокации и изменения цифр фиксированного плана нет.
Для нового спроса создаётся новый план.

## Item Ledger

Item Ledger содержит:

- append-only ленту физических движений;
- материальный остаток на cutoff;
- активные резервы живых планов;
- адресно-FIFO события покрытия потребностей пополнения.

Принятое поколение Ledger — единственный источник физических фактов.

## Очередь сборки и барабан

Очередь сборки автоматически состоит из незакрытого верхнеуровневого выпуска
всех живых планов. Барабан детерминированно раскладывает её по календарю,
участкам, тактам и мощности.

Барабан не владеет спросом, BOM, резервом или выполнением пополнения.
Ручной производственной программы DBR нет.

## Журналы исполнения

Производственный и закупочный журналы — две проекции одной потребности,
разделённые атрибутом `make/buy`.

Заказ является поручением исполнителю. Выпуск или поступление становится
выполнением только после появления принятого физического движения.

Для производимых деталей DBR проецирует зафиксированную потребность на даты
барабана. Полка удерживает расход защитного окна, а мехцех получает количество,
срок и приоритет без увеличения общего MRP. Контракт:
[`shelves-buffers-and-mechshop-pull.md`](shelves-buffers-and-mechshop-pull.md).

## Снимки

Расчёт выполняется вне GET-запроса, сохраняется и атомарно публикуется.
Страницы читают снимок с `ledger_generation`, `cutoff` и `truth_status`.

При неполном, stale или непринятом поколении зависимые значения недоступны.

## Frontend

React ERP-shell не повторяет доменную архитектуру отдельными модулями MRP и
DBR. Он собирает рабочие места из общих типизированных представлений:

- периодный план;
- очередь сборки и барабан;
- производственный журнал;
- закупочный журнал;
- карточка номенклатуры.

OpenAPI задаёт транспортные типы, `services` владеет HTTP, а UI использует
общие окна, таблицы, фильтры, состояния истины и диалоги. Подробно:
[`frontend-framework.md`](frontend-framework.md).
