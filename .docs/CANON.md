# КАНОН PRODPLAN

Этот файл обязателен для любого изменения системы. У каждой величины один
источник истины и один владелец расчёта. Параллельные движки запрещены.

Действующие решения владельца хранятся только в
`/home/ivan/PRODPLAN/mrp-decisions-log.md`. При противоречии код и остальные
документы исправляются по журналу решений.

## Ядро системы

PRODPLAN состоит из четырёх последовательно связанных контуров:

1. **План** фиксирует требуемый выпуск готовых изделий.
2. **MRP и Ledger резервов** один раз разворачивают BOM, фиксируют полные
   резервы и потребности пополнения.
3. **Журналы пополнения** показывают одну потребность, разделённую по способу
   пополнения `make` или `buy`.
4. **Очередь сборки и барабан** раскладывают во времени незакрытый выпуск
   готовых изделий всех живых планов.

Ни один нижестоящий контур не пересчитывает величины вышестоящего.

## Единственные источники

| Величина | Единственный источник |
|---|---|
| Физическое движение и остаток | принятое поколение Item Ledger |
| Исходный выпуск плана | зафиксированные строки периодного плана |
| Полная потребность BOM | зафиксированный `MrpRequirement` |
| Резерв плана | `ReservationEntry` |
| Потребность пополнения | зафиксированное поле резерва |
| Выполнение пополнения | FIFO-назначения физических пополнений на резерв |
| Остаток выпуска плана | исходный выпуск минус принятый выпуск этого плана |
| Очередь сборки | остатки выпуска всех живых планов, oldest-first |
| Календарная раскладка сборки | барабан поверх очереди сборки |
| Цель полки | расход барабана внутри защитного окна, ограниченный MRP |
| Количество вытягивания мехцеха | незакрытая MRP-потребность, ограниченная дефицитом полки |
| Исполнительный заказ | единый производственный или закупочный журнал |
| Факт выпуска | считанный назад результат проведения `СборкаЗапасов` в принятом Item Ledger |

Команда `Произвести` является каноническим исполнительным контуром: одним
действием она создаёт в 1С `СборкаЗапасов` и `СдельныйНаряд`. Создание
документов не считается фактом; факт появляется только после read-back
регистра проведения в Item Ledger и FIFO. Удаление этого контура запрещено.

## Неподвижное и подвижное

После фиксации плана неподвижны:

- строки выпуска плана;
- результат BOM-развёртки;
- полный резерв;
- покрытие наличием на cutoff;
- исходная потребность пополнения.

С поступлением фактов меняются только:

- покрытая часть потребности пополнения;
- остаток выпуска плана;
- положение незакрытого выпуска в барабане;
- состояние исполнительных заказов.

## Запрещено

- повторно разворачивать BOM зафиксированного плана;
- создавать несколько MRP-снимков одного плана;
- пересчитывать исходную потребность при refresh или поступлении;
- считать выполнение по статусам и накопительным полям заказов;
- создавать ручную производственную программу для барабана;
- строить барабан по одному выбранному плану или `program_id`;
- создавать отдельный спрос, NFP или буфер сверх MRP-потребности;
- терять невыполненную плитку при смене даты или поколения;
- приписывать физический факт произвольному заказу;
- использовать legacy-таблицу как fallback;
- сохранять в живой документации отменённую модель.

## Правила расширения

1. Новая функция читает существующую величину, а не вычисляет её второй раз.
2. Новый способ пополнения расширяет маршрутизацию, но не формулу потребности.
3. Оптимизаторы запуска, комплектности и раскроя ограничивают исполнение уже
   существующей потребностью; новый спрос они не создают.
4. DBR может менять срок, приоритет и удерживаемую на полке часть потребности,
   но не её общее количество.
5. Проекция и UI не содержат бизнес-математики.
6. Замена пути включает удаление старого пути и его документации.
7. Непринятый, неполный или stale Ledger даёт `unavailable`, а не ноль.

## Фронтенд

Фронтенд собирается как единый типизированный ERP-каркас. Одна backend-
сущность получает одно frontend-представление; разные рабочие места являются
режимами и фильтрами.

OpenAPI — источник транспортных типов. Страницы не вызывают HTTP напрямую,
не пересчитывают backend-величины и не создают собственные копии планов,
журналов или очередей. Контракт:
[`frontend-framework.md`](frontend-framework.md).

Любые предметные суммы, остатки, проценты, статусы, приоритеты, KPI,
группировки и доступные действия приходят готовыми из сохранённой backend
read-model. Frontend выполняет только форматирование и управление интерфейсом.

## Приёмка

Изменение принимается только если тесты доказывают:

- неизменность зафиксированного плана и резервов;
- один FIFO без двойного зачёта;
- сохранение незакрытого выпуска в очереди;
- детерминированную раскладку барабана;
- отсутствие ручного или параллельного источника спроса;
- fail-closed без legacy fallback.

## Механическая проверка

`tests/test_canon_invariants.py` существует и уже фиксирует непротиворечивость
действующих документов: наличие журнала решений и реестра владельцев,
канонические формулы и имена полей, отсутствие ссылок на удалённые контракты и
возврата отменённых пользовательских сценариев.

Файл включён в обязательный CI: workflow `.github/workflows/canon.yml` гоняет
`pytest -q tests/test_canon_invariants.py` в job `canon-invariants`, от которого
зависят job'ы `backend` и `frontend` — красный канон блокирует весь прогон.

До покрытия перечисленных ниже архитектурных инвариантов сведение кода ядра
не считается завершённым:

- фиксированный список писателей `ReservationEvent`;
- единственные точки записи документов в 1С;
- отсутствие второго хранилища физических остатков;
- отсутствие второго вычислителя reserve/replenishment/execution;
- отсутствие ручных DBR-программ и `program_id` как источника барабана;
- отсутствие предметной математики и прямого HTTP в frontend UI;
- один канонический `planning_run` на фиксированный план;
- отсутствие ссылок на несуществующую документацию.
