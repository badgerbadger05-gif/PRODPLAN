# Журнал изменений и прогресс разработки

Этот документ содержит ключевые изменения и реализованные функции в хронологическом порядке.

### Feature: Расчет норматива н/ч в распределении этапов (Сентябрь 2025)
- **Цель**: Добавить в распределение этапов расчетный норматив в нормо-часах и убрать лишнюю информацию.
- **Изменения**:
  - **Backend**:
    - В сервисе `stages_calculator.py` реализован расчет суммарного норматива (`norm_hours`) для каждого компонента и этапа. Расчет основан на сумме норм времени (`time_norm`) всех операций (`SpecOperation`) в дочерних спецификациях.
    - В схеме `schemas.py` убрано поле `replenishment_method` из базовой модели `ItemBase`, так как оно больше не используется в UI распределения.
  - **Frontend**:
    - На странице `StagesPage.vue` убрана колонка "Метод пополнения".
    - Добавлена колонка "Норматив н/ч", отображающая рассчитанное значение.
    - В заголовки вкладок этапов добавлен суммарный норматив по этапу для быстрой оценки.
- **Результат**: UI распределения этапов стал более информативным и сфокусированным на трудоемкости.

## UI/Frontend

### Исправление прокрутки и фиксация Layout (Сентябрь 2025)
- **Проблема**: Наблюдалось дублирование полос прокрутки (внутренняя у страницы и внешняя у `body`), а шапка и боковая панель "плавали" при скролле.
- **Решение**: Проведена стандартизация `QLayout` в `MainLayout.vue` с использованием стандартной модели `view="lHh Lpr lFf"`. Удалены конфликтующие CSS-правила и ручные вычисления высоты (`:style-fn`), которые приводили к созданию нескольких контейнеров прокрутки.
- **Результат**: Проблема двойного скролла устранена. Шапка и боковая панель теперь корректно зафиксированы.

## Backend и Функциональность

### Feature: Страница "Спецификация" (Дерево BOM) (Сентябрь 2025)
- **Цель**: Реализовать иерархическое представление состава изделия (BOM) для быстрого анализа и выявления ошибок в этапах и нормах.
- **API Endpoints**:
  - `GET /api/v1/specification/tree`: Для "ленивой" (lazy-load) загрузки дочерних узлов.
  - `GET /api/v1/specification/full`: Для рекурсивной загрузки полного дерева спецификации с защитой от циклов.
- **Реализация**:
  - **Backend**: Разработаны роутеры и сервисы для построения дерева. В узлы включены расчетные поля (`treeQty`, `treeTimeNh`), метод пополнения (`replenishmentMethod`) и предупреждения (`NO_STAGE`, `NO_TIME_NORM`, `CYCLE_DETECTED`).
  - **Frontend**: Создана страница `SpecificationPage.vue` с использованием `QTable` в режиме дерева. Реализована логика для полной загрузки и автоматического раскрытия всех узлов. UI был упрощен для фокусировки на просмотре полного дерева.

### Feature: Синхронизация данных из 1С (Сентябрь 2025)
- **Синхронизация Единиц Измерения (ЕИ)**:
  - Реализован сервис `units_sync.py` и эндпоинт `POST /api/v1/sync/units-odata`.
  - В UI кнопка "Синхронизация номенклатуры" теперь последовательно запускает синхронизацию номенклатуры и связанных с ней единиц измерения.
  - В API спецификации GUID единицы измерения теперь разрешается в человекочитаемое краткое наименование.
- **Синхронизация Наименований Операций**:
  - **Проблема**: В дереве спецификации для операций отображался прочерк вместо названия.
  - **Решение**: Создан сервис `operations_sync.py` и эндпоинт `POST /api/v1/sync/operations-odata`, который извлекает наименования операций из связанных данных 1С. На странице "Синхронизация" добавлена соответствующая кнопка.
### Fix: Распределение этапов (Гибка/Заготовка) и появление «Заготовительного цеха» (Сентябрь 2025)
- Проблема:
  - На странице распределения этапов некорректно распределялись позиции «Гибка» и «Заготовка».
  - «Заготовительный цех» не появлялся в выдаче распределения.

- Причина:
  - В ранней реализации в [calculate_resource_distribution()](backend/app/services/resource_calculator.py:78) внутри [expand()](backend/app/services/resource_calculator.py:117) этап компонента определялся по «внукам» — выбирался первый непустой stage_id из дочерней спецификации компонента. Это приводило к неверному маппингу ряда компонентов по участкам.
  - Дополнительно, «сборочные» этапы (например, «Сборка», «Завершение производства») на строке состава перекрывали реальные этапы изготовления вложенных деталей, из‑за чего «Заготовка» не попадала в распределение.

- Изменения (бэкенд):
  - В [calculate_resource_distribution()](backend/app/services/resource_calculator.py:78) переработан выбор stage_id:
    1) Базово используем stage текущей строки состава: чтение [SpecComponent.stage_id](backend/app/models.py:91).
    2) Если этап строки «сборочный» (имя этапа содержит «сбор» или «заверш») либо [component_type](backend/app/models.py:92) == «Сборка», игнорируем его (сбрасываем stage_id).
    3) Fallback: если stage_id не задан или игнорирован, берем первый непустой stage_id из дочерней спецификации («внуки»).
    4) В распределение попадают только позиции с методом пополнения «Производство».
  - Конкретные правки:
    - Блок выбора stage_id и fallback: [expand() — участок логики](backend/app/services/resource_calculator.py:145)
    - Добавлена фильтрация «сборочных» этапов по имени и component_type: [expand() — участок логики](backend/app/services/resource_calculator.py:145)

- Верификация (API):
  - Запрос распределения:
    - curl -s -X POST http://localhost:8000/api/v1/resources/calculate_distribution
  - Проверка наличия «Гибка» — в ответе присутствует ресурс «Гибочный цех» (resource_id=8) с компонентами, имеющими stage_name="Гибка".
  - Проверка этапа «Заготовка» (id=4) в распределении:
    - PowerShell: фильтрация по stage_id==4 показала наличие ресурса с id=6 (это «Заготовительный цех», возможны искажения кириллицы в консоли).
  - Проверка справочника этапов:
    - GET /api/v1/plan/stages — подтверждает, что «Заготовка» имеет value=4.
  - Проверка привязок этапов к участкам:
    - GET /api/v1/resources/ (список участков) + GET /api/v1/resources/{id}/stages — у ресурса id=6 присутствует stage_id=4.
  - Итог: «Заготовительный цех» появился в распределении, «Гибка» корректно отображается в «Гибочном цехе».

- Примечания:
  - При выводе в PowerShell встречались артефакты кодировки при печати русских символов в JSON (отображаются «?»). Это косметическая проблема консоли, не влияющая на API и UI.
  - Подбор участка при множестве кандидатов по одному этапу оставлен прежним: приоритет по совпадению имени участка со stage_name, далее — стабильный первый кандидат.

- Риски и совместимость:
  - Логика теперь предпочитает stage_id строки состава, но при «сборочном» этапе корректно смотрит в дочернюю спецификацию. Это улучшает детальность распределения и соответствует ожиданиям производственного процесса.
  - UI не менялся. Страница «Распределение этапов» сразу отражает результаты перерасчета.
