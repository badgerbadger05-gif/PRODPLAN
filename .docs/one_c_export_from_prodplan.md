# Выгрузка PRODPLAN в 1С

Статус: рабочий документ для доработки PRODPLAN. Дата: 2026-05-19.

Цель: описать, какие документы PRODPLAN должен создавать в 1С, в каком порядке, через какие OData EntitySet и какие документы 1С остаются источником обратной загрузки.

## Главный принцип

PRODPLAN становится операционным контуром планирования и производственного исполнения. 1С остается учетным контуром.

В 1С из PRODPLAN выгружаются только документы намерения и производственно-складские события, которые должны появиться в учете:

1. заказ на производство;
2. перемещение запасов;
3. выпуск/сборка запасов;
4. заказ поставщику.

Приходные накладные, оприходования и списания не создаются из PRODPLAN. Они создаются в 1С и затем импортируются обратно в PRODPLAN/ERPNext-слой как факт прихода или корректировки.

PRODPLAN может инициировать санкционированные исполнительные документы 1С.
Однако создание или проведение документа ещё не является фактом для
планирования. Фактом считается только обратное чтение его физического
движения в принятое поколение Item Ledger.

## Правило создания на основании

Дочерние документы, которые PRODPLAN создаёт в 1С, должны создаваться не как изолированные документы, а “на основании” родительского документа бизнес-цепочки. В OData это фиксируется полями:

- `ДокументОснование` — `Ref_Key` родительского документа 1С.
- `ДокументОснование_Type` — полный тип родительского документа, например `StandardODATA.Document_ЗаказНаПроизводство`.

Первичные документы, которые PRODPLAN сам вводит по результатам MRP, создаются без 1С-основания:

- `Document_ЗаказНаПроизводство`;
- `Document_ЗаказПоставщику`.

Подтверждённая цепочка:

| Создаваемый документ | Основание | Поля основания |
|---|---|---|
| `Document_ЗаказНаПроизводство` | первичный документ из MRP-потребности PRODPLAN | `ДокументОснование` не заполняется |
| `Document_ПеремещениеЗапасов` | `Document_ЗаказНаПроизводство` | `ДокументОснование=<Ref_Key заказа>`, `ДокументОснование_Type=StandardODATA.Document_ЗаказНаПроизводство` |
| `Document_СборкаЗапасов` | `Document_ЗаказНаПроизводство` | `ДокументОснование=<Ref_Key заказа>`, `ДокументОснование_Type=StandardODATA.Document_ЗаказНаПроизводство` |
| `Document_СдельныйНаряд` | `Document_СборкаЗапасов` | `ДокументОснование=<Ref_Key выпуска>`, `ДокументОснование_Type=StandardODATA.Document_СборкаЗапасов` |
| `Document_ЗаказПоставщику` | первичный документ из MRP-потребности PRODPLAN | `ДокументОснование` не заполняется |

Если основание неизвестно или родительский документ ещё не создан в 1С, дочерний документ выгружать нельзя. Допускается только `dry_run` с диагностикой причины.

### Кнопочная автоцепочка

Массовая фоновая выгрузка документов в 1С не используется. Если документы переносятся один к одному, то источник намерения должен быть явным пользовательским действием в PRODPLAN: кнопка в журнале, выбранная строка или выбранный документ.

Запуск кнопки для перемещения сначала выгружает недостающий родительский
заказ. Это правило реализовано в сервисе:

- `export_material_issues_to_1c` → вызывает `export_production_orders_to_1c` для тех `ProductionOrder`, у которых пуст `order_ref1c`.

По явной команде оператора PRODPLAN создаёт в 1С сборку запасов и сдельный
наряд через санкционированные экспортёры. Физический выпуск затем считывается
из регистра проведения в Item Ledger и только после принятия поколения
участвует в FIFO-выполнении.

Целевой процесс:

1. Пользователь в PRODPLAN выбирает конкретную строку/заказ и нажимает команду.
2. PRODPLAN валидирует локальные данные: номенклатура, склады, сотрудники, количество, основание, отсутствие успешного `sync_link`.
3. PRODPLAN сразу создаёт в 1С недостающий родительский документ и дочерние документы текущей команды.
4. Для `Document_ЗаказНаПроизводство` PRODPLAN заполняет текущую дату-время, организацию ЗСМ, производственную структурную единицу ЗСМ, `ЕдиницаИзмерения` в строках продукции, табличные части `Запасы` и `Операции`, затем сразу после создания выполняет штатное оперативное проведение через `Post?PostingModeOperational=true`.
   - `Запасы` строятся из компонентов спецификации изделия, количество = норма компонента * количество заказа.
   - `Операции` строятся из операций спецификации, `Нормочасы` = `НормаВремени` * количество заказа.
   - `СтруктурнаяЕдиницаРезерв_Key` и склад/структурная единица строк запасов берутся из привязки участка к складу (`workshop_warehouse_bindings`). Если привязки нет, PRODPLAN передаёт пустую ссылку, чтобы 1С не подставляла неверный склад по умолчанию.
5. Для `Document_ПеремещениеЗапасов` PRODPLAN заполняет текущую дату-время, организацию ЗСМ, `СтруктурнаяЕдиница_Key` для отправителя, `СтруктурнаяЕдиницаПолучатель_Key` для получателя и `ЕдиницаИзмерения` в строках запасов, создаёт документ непроведённым и показывает его в журнале заявок на перемещение. Фактическое складское движение выполняется отдельной кнопкой `Собрано`, которая вызывает `Unpost` + `Post?PostingModeOperational=true`.
6. PRODPLAN перечитывает из 1С `Ref_Key`, `Number`, `Posted`, сохраняет `sync_link` и локально продвигает статус только после подтверждения результата.
7. После успешного создания и проведения `Document_СдельныйНаряд` PRODPLAN закрывает родительский `Document_ЗаказНаПроизводство`: отправляет `PATCH {"СостояниеЗаказа_Key": "ad28565a-991b-11eb-e39a-fa163e61326a"}` и локально сохраняет состояние `Завершен`.
8. Если шаг цепочки упал, уже созданные документы не дублируются при повторном нажатии: повторный запуск продолжает цепочку от сохранённых `sync_link` и возвращает пользователю понятную ошибку по незавершённому шагу.

## Матрица направлений

| Процесс | Источник | Приемник | Документ 1С | Направление | Основание |
|---|---|---|---|---|---|
| Заказ на производство | PRODPLAN | 1С | `Document_ЗаказНаПроизводство` | PRODPLAN -> 1С | первичный документ из MRP, без 1С-основания |
| Перемещение между складами | PRODPLAN | 1С | `Document_ПеремещениеЗапасов` | PRODPLAN -> 1С | `Document_ЗаказНаПроизводство` |
| Передача материалов в производство | PRODPLAN | 1С | `Document_ПеремещениеЗапасов` или отдельное правило WIP | PRODPLAN -> 1С | `Document_ЗаказНаПроизводство` |
| Выпуск продукции | PRODPLAN | 1С | `Document_СборкаЗапасов` | PRODPLAN -> 1С | `Document_ЗаказНаПроизводство` |
| Сдельный наряд | PRODPLAN | 1С | `Document_СдельныйНаряд` | PRODPLAN -> 1С | `Document_СборкаЗапасов` |
| Заказ поставщику | PRODPLAN | 1С | `Document_ЗаказПоставщику` | PRODPLAN -> 1С | первичный документ из MRP, без 1С-основания |
| Приход от поставщика | 1С | PRODPLAN | `Document_ПриходнаяНакладная` | 1С -> PRODPLAN | создаётся в 1С на основании заказа поставщику |
| Оприходование фактических остатков | 1С | PRODPLAN | `Document_ОприходованиеЗапасов` | 1С -> PRODPLAN | создаётся в 1С, PRODPLAN не задаёт основание |
| Списание фактических остатков | 1С | PRODPLAN | `Document_СписаниеЗапасов` | 1С -> PRODPLAN | создаётся в 1С, PRODPLAN не задаёт основание |
| Сверка остатков | обе системы | отчет | регистры остатков 1С + остатки PRODPLAN | read-only | не применимо |

## Проведение документов 1С через OData

Подтверждено на демо-базе `unf_demo` для `Document_ПеремещениеЗапасов`, probe `ERPNext0001`:

- `PATCH {"Posted": true}` использовать нельзя. 1С меняет признак `Posted`, но не выполняет штатное проведение и не формирует движения регистров. Получается опасное состояние: документ выглядит проведённым, а движений нет.
- Рабочий способ проведения перемещения: сначала, при необходимости, вернуть документ в непроведённое состояние через `Unpost`, затем вызвать стандартную OData-команду `Post` в оперативном режиме.

Рабочая последовательность:

```http
POST /odata/standard.odata/Document_ПеремещениеЗапасов(guid'<Ref_Key>')/Unpost
POST /odata/standard.odata/Document_ПеремещениеЗапасов(guid'<Ref_Key>')/Post?PostingModeOperational=true
```

Практические условия:

- дата документа должна соответствовать требованиям оперативного проведения 1С; для теста `ERPNext0001` проведение прошло после смены даты на текущую;
- после успешного `Post?PostingModeOperational=true` проверено появление движения в отчёте 1С "Движение товаров по складам";
- `Post?PostingModeOperational=false` в тесте возвращал успех, но не дал ожидаемого движения по перемещению, поэтому для наших процессов по перемещениям закреплён именно оперативный режим;
- после проведения PRODPLAN должен перечитать `Posted=true` и обновлять локальный статус через read-only sync, а не выставлять `Posted` прямым `PATCH`.

## Нумерация документов PRODPLAN и 1С

Поле `Number` в 1С короткое. Длинный номер вида `ERPNext-TRANSFER-PROBE-0001` был обрезан 1С до `ERPNext-TRA`.

Правило:

- номер документа в PRODPLAN и `Number` в 1С должны совпадать для новых документов;
- все документы одной производственной цепочки используют общий ключ цепочки: `RRRROOOOO`, где `RRRR` — `source_run_id`, `OOOOO` — внутренний `production_order.order_id`;
- у дочерних документов меняется только префикс, а при нескольких документах одного типа добавляется буквенный хвост `A`, `B`, `C` по порядку создания;
- полный исходный ключ PRODPLAN дополнительно хранится в комментарии и таблице связей.

Формат:

| Документ | Формат | Пример |
|---|---|---|
| Заказ на производство | `PP{RRRROOOOO}` | `PP003300306` |
| Перемещение запасов | `MT{RRRROOOOO}{A..Z}` | `MT003300306A`, `MT003300306B` |
| Возвратное перемещение | `RT{RRRROOOOO}{A..Z}` | `RT003300306A` |
| Сборка/выпуск | `MF{RRRROOOOO}` или `MF{RRRROOOOO}{A..Z}` при нескольких выпусках | `MF003300306` |
| Сдельный наряд | `PW{RRRROOOOO}` или тот же хвост, что у выпуска | `PW003300306` |
| Заказ поставщику | `PO{run_id:05d}{index:03d}` | `PO00033001` |

Если у заказа несколько перемещений из разных складов, они получают один общий ключ и разные хвосты:

```text
PP003300306
MT003300306A
MT003300306B
MF003300306
PW003300306
```

Минимальный маркер в 1С:

```text
Комментарий = PRODPLAN source=<doctype>/<id>; run=<sync_run_id>
```

## Порядок работы по кнопке

Пакетный регламент не создаёт документы в 1С. Документы создаются только пользовательскими командами:

| Команда PRODPLAN | Что создаётся в 1С | Дополнительное действие |
|---|---|---|
| `Запустить в 1С` | `Document_ЗаказНаПроизводство`, затем `Document_ПеремещениеЗапасов` для выдачи компонентов | заказ на производство сразу проводится оперативно; перемещение остаётся непроведённым и попадает в журнал заявок на перемещение |
| `Собрано` в журнале заявок на перемещение | проведение ранее созданного `Document_ПеремещениеЗапасов` | перемещение проводится через `Unpost` + `Post?PostingModeOperational=true`; в журнале заказов колонка `Обеспечение` становится `Собрано` |
| `Произвести` | `Document_СборкаЗапасов`, затем `Document_СдельныйНаряд` | 1С проводит оба документа; PRODPLAN сразу считывает регистр проведения и передаёт подтверждённый факт в Item Ledger и FIFO |
| `Заказать` / `В 1С` по закупке | `Document_ЗаказПоставщику` | первичный документ из MRP-потребности без 1С-основания |

Фоновые задачи допускаются только для чтения и сверки:

1. обновить справочники и маппинги, необходимые для кнопочных действий: номенклатура, единицы, склады, участки, поставщики, сотрудники;
2. импортировать из 1С факты прихода, оприходования, списания и состояния проведённых документов;
3. выполнять read-only сверку остатков и статусов;
4. обновлять локальные статусы PRODPLAN по подтверждённым данным 1С.

Кнопка `Произвести` создаёт исполнительные документы, но это ещё не факт.
Фактом является только считанный назад результат проведения в 1С,
импортированный как физическое движение Item Ledger; только принятое
поколение Ledger меняет выполнение потребности и плана.

Если заказ на производство не выгрузился в 1С, связанные производственные движения не должны уходить в 1С без основания.

## Идемпотентность

Нужна таблица связей, чтобы повторный запуск не создавал дубль.

Минимальные поля `sync_link`:

| Поле | Назначение |
|---|---|
| `source_system` | `PRODPLAN` |
| `source_doctype` | тип исходного документа PRODPLAN |
| `source_id` | внутренний id исходного документа |
| `target_system` | `1C` |
| `target_entity` | OData EntitySet 1С |
| `target_ref_key` | `Ref_Key` документа 1С |
| `target_number` | короткий номер документа 1С |
| `payload_hash` | hash нормализованного payload |
| `status` | `planned`, `success`, `error`, `cancelled` |
| `last_error` | последняя ошибка записи |
| `last_synced_at` | дата последней успешной синхронизации |

Курсор нужен только для read-only синхронизаций и сверок. Для write-сценариев главным механизмом является `sync_link`, потому что каждая кнопка создаёт конкретный документ или конкретную цепочку документов.

Курсор read-only этапов хранить отдельно, например:

| Этап | Ключ идемпотентности | Курсор |
|---|---|---|
| purchase_receipt_import | `Ref_Key` 1С | `Date`, `Ref_Key` |
| stock_adjustment_import | `Ref_Key` 1С | `Date`, `Ref_Key` |
| posted_transfer_sync | `Ref_Key` 1С | `Date`, `Ref_Key` |

## Безопасность записи

Все write-сценарии сначала выполнять только на `unf_demo`.

Защита в коде должна проверять:

1. профиль окружения: `demo`;
2. URL содержит `unf_demo`;
3. явный флаг записи включен;
4. для каждого этапа указан разрешенный `EntitySet`;
5. для дочерних документов есть подтверждённое основание (`ДокументОснование` + `ДокументОснование_Type`);
6. dry-run не пишет в 1С и не двигает курсоры.
7. write-запрос пришёл из явной пользовательской команды, а не из фонового массового регламента.

Рабочую базу `unf` подключать только после проверки полного пакета на демо-копии.

## Что не делать

1. Не создавать в 1С приходные накладные из PRODPLAN.
2. Не создавать в 1С оприходования и списания из PRODPLAN.
3. Не выгружать агрегированный остаток как факт движения.
4. Не перезаписывать остатки в PRODPLAN/ERPNext напрямую без складского документа.
5. Не создавать повторный документ в 1С, если уже есть `sync_link` с успешным `Ref_Key`.
6. Не выставлять `Posted=true` прямым `PATCH`; для проведения использовать только стандартные OData-команды `Unpost`/`Post`, а для `Document_ПеремещениеЗапасов` — подтверждённый режим `Post?PostingModeOperational=true`.
7. Счётчик успешно созданных документов в ответе экспорта увеличивается только после успешного создания, записи sync_link и выполнения обязательного пост-шага; если оперативное проведение заказа не прошло, строка считается ошибочной и не маскируется как проведённая.
8. Для всех табличных частей, где metadata 1С содержит `ЕдиницаИзмерения` / `ЕдиницаИзмерения_Type`, PRODPLAN передаёт GUID единицы из `items.unit` с типом `StandardODATA.Catalog_КлассификаторЕдиницИзмерения`.
7. Не создавать дочерние документы 1С без заполненного и проверенного основания.
8. Не запускать массовую write-выгрузку документов в 1С фоновым процессом.

## Открытые решения

1. Какой короткий формат номера использовать в бою: `PP00000001`, `ERPNext0001` или отдельный префикс 1С.
2. Нужно ли отражать WIP-передачу отдельным перемещением в 1С.
3. Какие реквизиты 1С обязательны для проведения документов кроме `Document_ПеремещениеЗапасов`: организация, склад, подразделение, операция, хозяйственная операция, состояние, ответственный.
4. Как обрабатывать отмены, сторно и возвраты поставщику.

## Физический read-back

Выпуск, поступление, перемещение, возврат и корректировка импортируются как
физические движения `stock_ledger_entry`. `sync_link` сохраняет происхождение
документа, но не заменяет движение и не определяет выполнение по статусу.
