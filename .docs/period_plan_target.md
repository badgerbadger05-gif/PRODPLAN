# Целевая логика страницы «Период план»

Фиксирует контракт фичи `Period Plan` в ERP-shell, чтобы UI-итерации шли от
письменной спецификации, а не «не нравится / переделай».

> **Источник истины:** план и MRP-снимок фиксируют обязательства, но не факт.
> Исполнение журнала вычисляется только из адресных allocation принятого
> поколения Item Ledger согласно
> [`planning-truth-contract.md`](planning-truth-contract.md). При пустом,
> stale или непринятом Ledger исполнение недоступно: нельзя показывать нули,
> проценты из legacy-полей или разрешать зависящие расчёты/мутации. Страница
> открывает сохранённый снимок; пересчёт выполняется фоновым worker.

## Назначение

Период план — это фиксированный горизонт **производственной потребности**,
выраженный матрицей `номенклатура × неделя (пятница)`. Из зафиксированного
периодного плана через MRP-снимок порождается фиксированный набор
`MrpRequirement`/`MrpRequirementBucket` и плановые `PlannedOrder` /
`PlannedPurchase` / `PlannedRework`. Журнал исполнения показывает, что и кем
покрыто, что осталось закупить / переработать / произвести.

## Жизненный цикл

```
        ┌──────────┐                  ┌─────────┐                       ┌──────────┐
        │  draft   │ ── зафиксиров. ──▶│  fixed  │ ─── в архив ────────▶│ archived │
        │ редакт.  │                  │ MRP run │ ◀── из архива ───────│          │
        └────┬─────┘                  └────┬────┘                       └──────────┘
             │                              │
             │                              ▼
             │                      MRP-снимок (run)
             │                  PlannedOrder/Purchase/Rework
             │                              │
             └───────  удалить ─────────────┘
                       (если нет SUCCESS run)
```

## Состояния плана

| status     | что разрешено                                                    | UI               |
|------------|-------------------------------------------------------------------|------------------|
| `draft`    | редактирование шапки (PATCH), матрицы, добавление/удаление строк, фиксация | список + детальное окно с редактированием |
| `fixed`    | MRP-снимок, ре-аллокация, переход в архив; матрица read-only (кроме незаблокированных ячеек, если правила это позволят в будущем) | список + детальное окно с journal |
| `archived` | возврат из архива; всё прочее заблокировано                       | в списке тусклый, в детальном окне только «Из архива» |

## Удаление

- План удаляется через `DELETE /v1/plan/period-plans/{id}`.
- Бэкенд отказывает, если есть хотя бы один `planning_run` со
  `source_plan_id = id` и `status = 'SUCCESS'` — иначе мы потеряли бы
  фиксированный MRP-результат, на который ссылаются `PlannedOrder` и
  `MrpRequirement`.
- Архивные планы удалять нельзя из UI (исторический срез не трогаем).

## Матрица

- **Шаг** — пятницы между `period_from` и `period_to` включительно. Никаких
  частичных недель, никаких других дней недели.
- **Локализация ячейки** = `(item_id, bucket_date)`. Уникальный ключ —
  `(plan_id, item_id, bucket_date)`.
- **Locked-ячейка** — `production_plan_line.locked_by_run_id IS NOT NULL`.
  Значит, MRP-снимок этой ячейки уже посчитан и эту цифру менять нельзя,
  иначе расчёт расходится. В UI: заштрихованный фон, не редактируется.
- **Dirty-ячейка** в UI — введённое, но ещё не сохранённое значение.
  Фон `#fff9e0`. До нажатия «Сохранить» / «Отмена» нельзя зафиксировать план.
- **Двойной клик** на черновой ячейке — копирует её значение в остальные
  доступные ячейки строки. Кнопка `≡` в строке — равномерно делит итог
  строки по доступным ячейкам.
- **`<tfoot>` итоги** считаются с учётом dirty.

## Подбор номенклатуры

- Поиск идёт через общий эндпоинт `/v1/nomenclature/search` (тот же, что
  использует «План выпуска квартальный») — то есть с эмбеддингами, если они
  доступны, иначе текстовым ILIKE по `item_name | item_article | item_code`.
- Поведение поля:
  - дебаунс 200 мс, минимальная длина запроса — 2 символа;
  - выпадающий список под инпутом, навигация `↑/↓`, выбор `Enter`,
    `Escape` закрывает;
  - после выбора вызывается `ensure_item` (создаёт `Item` если ещё нет) и
    затем `POST /v1/plan/period-plans/{id}/items`, который добавляет
    нулевую строку в первую пятницу периода.

## Фиксация

- Триггеры на кнопку «Зафиксировать»:
  1. план `draft`;
  2. нет dirty-изменений (иначе ошибка «сначала Сохранить или Отмена»);
  3. в матрице есть хотя бы одна ячейка со значением `> 0` (иначе ошибка
     «нельзя зафиксировать пустой план»);
  4. подтверждение пользователя (confirm).
- После фиксации план переводится в `fixed`, выставляются `fixed_at` /
  `fixed_by`. Сразу становится доступна кнопка «MRP снимок».

## MRP-снимок и журнал

- На один период план может быть много `planning_run` со
  `source_plan_id = id`. Историю показываем в дропдауне «Прогон» во вкладке
  «Журнал исполнения». По умолчанию выбран последний run или тот, который
  только что создан.
- «Ре-аллокация» вызывает `POST /v1/plan/results/{run_id}/purchases/allocate`
  и `…/rework/allocate` для активного run.
- Фильтры журнала: поток (production/purchase/rework), уровень BOM,
  покрытие (Все / Покрыто ≥95% / Частично / Не покрыто).
- Сортировка по колонкам (клик по заголовку), экспорт CSV.
- Производственные строки `planned_order` в period-plan MRP получают
  реальные `start_date` / `finish_date` через `CapacityScheduler`: если
  заказ уже нельзя разместить до даты потребности, мощностной расчет
  сдвигает его вправо. API дополнительно отдаёт динамические поля
  `forecast_date`, `forecast_shift_days`, `forecast_reason`.
- Матрица плана показывает прогноз смещения рядом с количеством в недельной
  ячейке (`+N дн · дата`) по последнему `FIXED_SNAPSHOT` для плана.
  Журнал исполнения и журнал заказов показывают тот же индикатор рядом с
  датами задания/плана, чтобы пользователь видел реальную картину без
  изменения исходного планового количества.

## Архив

- `POST /v1/plan/period-plans/{id}/archive` — из любого статуса кроме уже
  `archived`.
- `POST /v1/plan/period-plans/{id}/unarchive` — только из `archived`; план
  возвращается в `fixed` если был `fixed_at`, иначе в `draft`.

## Архитектурные инварианты

- Полноценное окно вместо модалки/split — клик по строке плана **заменяет**
  содержимое того же `DocumentWindow`. Возврат через «К списку планов» или
  `Esc`.
- Любая мутация (`PATCH`, `POST items`, `POST lines/bulk_upsert`, `archive`,
  `unarchive`, `fix`) запрашивает данные плана заново (`getPeriodPlanMatrix`)
  — UI не пытается локально мержить, чтобы избежать дрифта с БД.
- Поля `fixed_by` / `created_by` берутся бэкендом, фронт не подсовывает
  «erp-shell» жёстко.

## Открытые вопросы

- Нет частичной разморозки `fixed`-плана (возврат в `draft`). По текущей
  логике зафиксированный план может только пойти в архив или быть
  пересчитан новым MRP-снимком.

## Реализованные уточнения

- Автогенерация `comment` реализована в `create_period_plan()`: «МАЙ 2026» /
  «МАЙ–ИЮНЬ 2026» по периоду.
- Deep-link из журнала исполнения реализован: `production_order` открывает
  журнал заказов, `planned_order` / `planned_purchase` / `planned_rework`
  открывают соответствующую вкладку MRP-результата.
