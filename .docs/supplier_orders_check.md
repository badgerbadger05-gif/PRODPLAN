# Учет заказов поставщику 1С при расчете потребностей

## Статус документа

Документ фиксирует целевую логику и текущее состояние реализации.

На 2026-05-08 подтверждена логика статусов 1С для признака "деталь уже заказана":
- не учитываем статус `"Новый заказ"`;
- не учитываем статус `"Отменен"`;
- не учитываем статус `"Завершен"` / `"Завершён"` и производные закрывающие статусы вроде `"Завершен успешно"`;
- не учитываем удаленные заказы (`DeletionMark = true`);
- все остальные статусы считаются заказанными и должны уменьшать будущую потребность на закупку.

Остаются открытыми правила фактического поступления:
- по каким документам и полям считать факт поступления;
- как считать остаток к поступлению по частично/полностью поступившим строкам;
- как обрабатывать строки без даты поступления;
- точное поле/формат статуса заказа поставщику в OData.

Реализация 2026-05-08:
- добавлены поля состояния/удаления/остатка к поступлению для заказов поставщику;
- MRP уменьшает `planned_purchase` на неудаленные заказы поставщику со статусом не `"Новый заказ"`, не `"Отменен"` и не `"Завершен"`;
- учитываются только строки с `delivery_date <= need_date`;
- строки без `delivery_date` пока не участвуют в автоматическом покрытии потребности.

## Разделение сущностей

1) Заказы поставщику в 1С — документы `Document_ЗаказПоставщику`
- Используем только как входные данные для расчета.
- Не создаем и не обновляем из PRODPLAN.
- Не связываем напрямую с плановыми закупками PRODPLAN.

2) Плановые закупки PRODPLAN — таблица `planned_purchase`
- Создаются MRP-расчетом.
- Отражают только то, что еще нужно заказать после учета остатков и уже размещенных заказов поставщику.

Следствие:
- Заказы поставщику из 1С должны работать как "уже заказанное, но еще не поступившее".
- MRP не должен создавать новую закупку на количество, которое уже покрыто активным заказом поставщику.

## Аналогия с активными заказами на производство

Сейчас для активных заказов на производство 1С есть два эффекта:

A) Готовая деталь уже заказана к производству.
- Новая потребность на выпуск этой детали уменьшается на `remaining_qty` активных заказов на производство.

B) Активный производственный заказ занимает компоненты.
- Компоненты из BOM резервируются под незавершенный выпуск и уменьшают доступный `stock_by_item`.

Для заказов поставщику нужен аналог эффекта A для закупаемых позиций:

S) Деталь/материал уже заказан поставщику.
- Новая потребность на закупку этой позиции уменьшается на остаток к поступлению по активным заказам поставщику.

Эффект B для заказов поставщику не нужен: заказ поставщику не потребляет компоненты по BOM, он является будущим приходом конкретной номенклатуры.

## Целевая логика

Цель: при расчете потребностей не создавать закупки сверх того, что уже заказано поставщикам в 1С и еще не поступило.

Предварительное правило:
- Для каждой строки активного заказа поставщику считаем `remaining_qty_to_receive`.
- При формировании `planned_purchase` уменьшаем закупочную потребность по `item_id` на доступный остаток активных заказов поставщику.
- Учет должен быть количественным и желательно датированным по `delivery_date`.

Базовая формула:

`purchase_need_adj(item, need_date) = max(purchase_need(item, need_date) - available_supplier_order_qty(item, need_date), 0)`

Где `available_supplier_order_qty` — сумма остатков к поступлению по активным заказам поставщику, которые можно использовать для закрытия потребности.

## Датирование

Предпочтительная логика:
- Если у строки заказа поставщику есть `delivery_date`, она закрывает потребность с датой `need_date >= delivery_date`.
- Если `delivery_date` позже потребности, такая строка не должна автоматически закрывать раннюю потребность.

Открытый вопрос:
- Что делать со строками без `delivery_date`:
  - учитывать без даты как ближайшее поступление;
  - учитывать только в общем количестве, но писать warning;
  - не учитывать до заполнения даты.

Рекомендуемый вариант для будущей реализации: не учитывать строки без даты в автоматическом уменьшении потребности и выводить диагностическое предупреждение. Но это решение нужно подтвердить с пользователями.

## Статусы и признак "уже заказано"

Подтвержденное бизнес-правило:
- статус `"Новый заказ"` — не считается заказанным и не уменьшает потребность MRP;
- статус `"Отменен"` — не считается заказанным и не уменьшает потребность MRP;
- статус `"Завершен"` / `"Завершён"` — не считается заказанным и не уменьшает потребность MRP, потому что заказ закрыт и выполнен;
- удаленный заказ (`DeletionMark = true`) — не считается заказанным и не уменьшает потребность MRP;
- любой другой неудаленный статус — считается заказанным и уменьшает потребность MRP на остаток к поступлению.

Из меню 1С на 2026-05-08 видны статусы:
- `Новый заказ` — исключить из учета;
- `В закупку` — учитывать;
- `Оплачен частично` — учитывать;
- `Оплачены полностью` — учитывать;
- `Получен авансом` — учитывать;
- `Отправлен по России` — учитывать;
- `Принят на склад` — учитывать;
- `Завершен успешно` — исключить из учета;
- `Отменен` — исключить из учета.

Техническое правило для будущей реализации:

`supplier_order_is_ordered = deletion_mark == false and order_state_name not in ("Новый заказ", "Отменен", "Завершен")`

Если надежнее хранить GUID состояния, то в коде лучше сравнивать `order_state_key` с GUID статусов `"Новый заказ"`, `"Отменен"` и `"Завершен"`, а `order_state_name` использовать для диагностики и UI.

`Posted` не должен становиться главным признаком заказанности без отдельного подтверждения. Подтвержденный признак сейчас — именно состояние заказа.

## Данные, которые уже есть

Текущие таблицы:
- `supplier_orders`
- `supplier_order_items`
- `suppliers`

Текущая синхронизация:
- `backend/app/services/supplier_order_sync.py`
- endpoint: `POST /sync/supplier-orders-odata`

Сейчас сохраняется:
- шапка заказа: номер, дата, `Ref_Key`, поставщик, сумма, `Posted`;
- строки: номенклатура, количество, цена, сумма, `ДатаПоступления`.

Ограничения текущей модели:
- нет `DeletionMark`;
- нет состояния заказа и GUID состояния;
- нет номера строки / уникального идентификатора строки;
- нет факта поступления;
- нет `received_qty`;
- нет `remaining_qty_to_receive`;
- строка сейчас ищется по `(order_id, item_id)`, что плохо для заказов с несколькими строками одной номенклатуры.

## Что понадобится добавить в БД

В `supplier_orders`:
- `order_state_key` — GUID состояния заказа поставщику;
- `order_state_name` — человекочитаемое состояние для диагностики;
- `deletion_mark` — признак удаления из 1С;
- `is_posted` оставить как отдельный диагностический признак, но не использовать как главный фильтр заказанности.

В `supplier_order_items`:
- `line_number` или другой стабильный идентификатор строки из 1С;
- `item_id_ref` уже есть как ссылка на `items.item_id`;
- `quantity` — заказанное количество;
- `received_qty` — фактически поступившее количество;
- `remaining_qty` — остаток к поступлению;
- `delivery_date` — ожидаемая дата поступления;
- возможно `characteristic_ref1c`, если в заказах поставщику используются характеристики.

Нужна миграция Alembic и обновление SQLAlchemy/Pydantic-схем.

## Факт поступления

Для корректного `remaining_qty` нужно понять источник факта.

Открытые вопросы:
- Какой документ 1С закрывает заказ поставщику фактом поступления.
- Есть ли в документе поступления ссылка на `ЗаказПоставщику_Key`.
- Есть ли ссылка на номер строки или только на номенклатуру.
- Нужно ли учитывать возвраты/корректировки.

Целевая формула:

`remaining_qty = max(ordered_qty - received_qty, 0)`

Если прямой связи поступления с заказом нет, потребуется отдельная стратегия сопоставления. До подтверждения связи с фактом поступления безопаснее не использовать заказы поставщику в MRP.

## Интеграция в MRP

Текущая интеграция:

1) Синхронизация:
- `supplier_order_sync.py` загружает состояние, удаление, номер строки, ожидаемую дату поступления и расчетный остаток к поступлению;
- отдельная синхронизация факта поступления пока не реализована, потому что источник факта еще не подтвержден.

2) Подготовка данных расчета:
- `_get_active_supplier_remaining_by_item_date(db)` возвращает остатки к поступлению по `item_id` и `delivery_date`;
- фильтруются только учитываемые строки с `remaining_qty > 0`.

3) Формирование закупок:
- в `build_planned_orders_and_purchases()` для `is_purchase` `requested_qty_raw` уменьшается на доступный остаток заказов поставщику;
- использованное количество списывается из локального кэша, чтобы один заказ поставщику не закрывал несколько потребностей дважды;
- при частичном покрытии создается `planned_purchase` только на остаток.

4) Диагностика:
- отдельный UI/экспорт диагностики покрытия пока не реализован.

## Предлагаемые тесты после реализации

1) Заказ поставщику в учитываемом статусе полностью закрывает потребность:
- статус не `"Новый заказ"`, не `"Отменен"`, `DeletionMark = false`;
- потребность 10, активный остаток к поступлению 10;
- `planned_purchase` не создается.

2) Заказ поставщику в учитываемом статусе частично закрывает потребность:
- статус не `"Новый заказ"`, не `"Отменен"`, `DeletionMark = false`;
- потребность 10, активный остаток к поступлению 4;
- создается `planned_purchase` на 6.

3) Поздняя дата поступления не закрывает раннюю потребность:
- потребность 2026-05-10, заказ поставщику на 2026-05-20;
- закупка на раннюю дату остается.

4) Один заказ поставщику не используется дважды:
- две потребности по 5, активный остаток 6;
- первая закрыта на 5, вторая закрыта только на 1.

5) Заказ поставщику в статусе `"Новый заказ"` не участвует:
- остаток не уменьшает закупочную потребность;
- `planned_purchase` создается на полную потребность.

6) Заказ поставщику в статусе `"Отменен"` не участвует:
- остаток не уменьшает закупочную потребность;
- `planned_purchase` создается на полную потребность.

7) Заказ поставщику в статусе `"Завершен"` не участвует:
- остаток не уменьшает закупочную потребность;
- `planned_purchase` создается на полную потребность.

8) Удаленный заказ поставщику не участвует:
- `DeletionMark = true`;
- остаток не уменьшает закупочную потребность.
