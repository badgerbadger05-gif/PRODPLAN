## Краткий вывод

Shadow содержит одновременно несколько связанных повреждений:

1. июньский план был заморожен до доступной исторической границы физического
   импорта и поэтому получил нулевой начальный склад;
2. сохранённые stock-allocation старых планов могут увести общий пул в минус,
   после чего дефицит старых планов прибавляется к `net_required_qty` нового
   плана;
3. один физический факт повторно создаёт несколько `ReservationEvent realize`;
4. журнал закупок не вычитает покрытие открытыми заказами поставщика и называет
   «к заказу» всё ещё не поступившее количество;
5. accepted assembly queue пуста, поэтому барабан также пуст;
6. frontend во время долгого запроса показывает пустую таблицу и пустые
   идентификаторы снимка, из-за чего загрузка выглядит как отсутствие данных.

Текущие проценты выполнения и текущий остаток «к заказу» нельзя использовать
для операционных решений.

## 2. Июньский план заморожен с нулевым складом

Серверный сценарий восстановления `reconstruct.py` задаёт:

```text
OPENING = 2026-06-02T00:00:00+00:00
первый plan cutoff = 2026-06-02T14:12:50+00:00
```

Но сохранённый `mrp_freeze_baseline` run 2 имеет:

```text
baseline_at = 2026-05-31 23:59:59.999999
baseline rows = 1441
sum(stock_qty) = 0
positive stock rows = 0
negative stock rows = 0
```

То есть MRP запросил физический baseline раньше начала импортированной истории.
Результат:

```text
MrpRequirement rows = 1441
rows where net_required_qty = total_required_qty = 1441
```

Весь июньский BOM был признан чистой потребностью, как если бы складских
остатков и покрытия вообще не существовало. Это непосредственно объясняет
`247253.950` BUY qty run 2 и основной июньский пик.

## 3. Дефицит старых allocation переносится в новый план

В `backend/app/services/mrp_freeze.py` retained stock-allocation активных старых
прогонов вычитаются из текущего пула:

```python
pools.stock[item_id] = pools.stock.get(item_id, 0.0) - active_qty
```

Ограничения нулём и fail-closed проверки недостаточного текущего остатка здесь
нет. Затем `period_plan_service.py` использует отрицательный `stock_left`:

```python
after_stock = q - stock_left
```

При отрицательном `stock_left` старый дефицит прибавляется к потребности нового
плана.

Фактический результат в run 11:

```text
MrpRequirement rows                  885
net_required_qty > total_required_qty 501
суммарное превышение                 167259.826
```

Показательный пример:

```text
Номенклатура: Шайба плоская М10 DIN 125
item_id: 10873
gross / total_required_qty: 3468
net_required_qty:           32687
превышение:                 29219

retained stock allocations старых runs: 41586
текущий baseline stock:                 12367
41586 - 12367 =                         29219
```

Таким образом, предположение о том, что последующий расчёт «добирает остатки»
предыдущих расчётов и записывает их в новый план, подтверждено точно.

## 4. Один физический факт зачтён несколько раз

В `reservation_event` принятого поколения 27:

```text
групп sle_id с несколькими realize events: 4508
лишних realize events:                    5014
повторно зачтённое количество:            119219.232
максимум событий на один sle_id:          6
```

В execution journal встречаются две реализации с одинаковыми:

```text
stock_ledger_entry_id
fact_ref
fact_line_ref
realized_delta
```

но разными `ReservationEvent.id`.

Это нарушает основной инвариант: один физический факт учитывается один раз.
Следствия:

- числители выполнения завышены;
- FIFO-потребности закрываются преждевременно;
- проценты `40%`, `85.9%`, `24.4%` нельзя считать достоверными;
- верхнеуровневый выпуск мог быть закрыт повторно, что согласуется с пустой
  assembly queue.

Существующие тесты и CANON-гейт не проверяют фактическую уникальность
`sle_id` среди событий реализации опубликованного поколения.

## 5. «К заказу» сейчас означает «не поступило»

В плане №1 UI показывает:

```text
Закупка: покрыто 24.4% · к заказу 75.6%
```

Backend `period_plan_service.py` считает:

```text
purchase_covered_qty = replenishment_received_qty
purchase_to_order_qty =
    replenishment_required_qty - replenishment_received_qty
```

Открытые заказы поставщика не вычитаются.

В `purchase_control_snapshot.py` для BUY-строк явно установлено:

```python
open_order_covered = 0.0
coverage_slices = []
```

Поэтому `75.6%` — это доля, которая физически ещё не поступила, а не точное
количество, которое надо заказать.

Текущий purchase snapshot 79:

```text
Ledger generation: 27
raw rows:          680
active rows:       579
line_status=to_order для всех active rows
```

Разбивка сохранённой потребности:

|---|---:|---:|
| Июнь 2026 | 608 | 193316.214 |
| до 03.07.2026 | 8 | 536.000 |

До восстановления allocation открытых заказов журнал не должен разрешать
материализацию всего `to_order_qty`.

## 7. Журналы не полностью пусты — frontend маскирует загрузку

Прямой API журнала производства возвращает:

```text
total = 60
HTTP 200
```

Прямой API журнала закупок возвращает:

```text
total = 579 active rows
snapshot_id = 79
ledger_generation = 27
HTTP 200
```

Во время поднятия VPN отдельные запросы занимали 10–20 секунд. Frontend в это
время:

- оставляет таблицу полностью пустой;
- показывает `Снимок: — · Ledger: —`;
- выводит малозаметное `Загрузка...` только в status bar;
- блокирует кнопки;
- не отличает «данных нет» от «ответ ещё не получен».

На странице закупок таблица также визуально обрезается правой частью рабочей
области. Это отдельные frontend-дефекты, не причина повреждения MRP.

## Что нельзя делать

До исправления причин нельзя:

- формировать заказы из всех текущих строк `to_order`;
- принимать текущие проценты выполнения как факт;
- запускать новый MRP поверх повреждённых retained allocation;
- вручную наполнять барабан;
- чинить данные точечными `UPDATE` без полного воспроизводимого rebuild;
- применять исправления к stable до проверки на отдельной копии shadow.

## Рекомендуемый порядок исправления

1. Добавить fail-closed проверку исторической границы:
   `stock_baseline_at` не может быть раньше доступного opening физического
   импорта.
2. Запретить отрицательный retained stock pool. Недостаток текущего физического
   остатка относительно старого allocation должен диагностироваться отдельно,
   а не прибавляться к новому `net_required_qty`.
3. Добавить инвариант:
   `net_required_qty <= total_required_qty` для обычной MRP-потребности.
   Если бизнес-модель требует отдельно учитывать старый дефицит, он должен
   иметь отдельного владельца и provenance, а не маскироваться как спрос нового
   плана.
4. Обеспечить уникальность физического зачёта:
   один `sle_id` не может создавать более одного количественного `realize`
   в одном опубликованном поколении.
5. Найти путь, который повторно создал 5014 событий, и покрыть его
   идемпотентным integration-тестом historical replay → refresh → publish.
6. Восстановить allocation открытых заказов поставщика на BUY reservations.
7. Переименовать текущий показатель в «не поступило», пока
   `open_order_covered_qty` не является реальным.
8. После исправления кода восстановить shadow из проверенного backup и
   воспроизвести историю с opening, покрывающим первый freeze cutoff.
9. До публикации проверить:
   - ни одного duplicate `sle_id` realization;
   - ни одной строки `net > gross`;
   - один FIFO без двойного зачёта;
   - сумма журнала закупок раскладывается как
     `received + open_order_covered + to_order = required`;
   - assembly queue содержит незакрытый выпуск всех живых планов;
   - барабан содержит очередь либо объяснимые gaps.
10. После backend-проверок исправить frontend loading/error/empty states и
    геометрию таблицы закупок.
