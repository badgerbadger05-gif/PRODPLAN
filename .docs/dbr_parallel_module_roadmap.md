# Роадмап: параллельный модуль планирования «Барабан + Питатели» (DBR) в PRODPLAN

Дата: 2026-07-16. Статус: черновик для обсуждения.

## 1. Зачем и что переносим

ERPNext запустить в эксплуатацию не удаётся, но реализованная там система планирования
(кастомное приложение `prodflow`, репозиторий `/home/ivan/prodflow-erpnext`) — рабочая и
проверенная по дизайну: **Производственная программа → Барабан (выровненный график финальной
сборки) → Питатели (мехцех / гальваника / закупка) со складами-магазинами и трёхзонными
DDMRP-буферами**. Ветка `feat/prodflow-planning` влита в main 2026-07-10
(«stabilize drum and feeder planning»).

Решение: перенести эту систему в PRODPLAN как **параллельный модуль**:

- общая БД PostgreSQL и общие синхронизации 1С (ничего не досинхронизируем — всё нужное уже
  приходит: номенклатура, спеки, остатки по складам, заказы на производство/поставщикам,
  участки, календарь);
- общие экспортные ручки в 1С (`one_c_*_export` + `sync_link`);
- **свой** расчётный модуль (`services/dbr/`), **свои** таблицы (`dbr_*`), **свой** раздел UI;
- существующий контур планирования (planning_service / period_plan / mrp_reconciliation)
  не трогаем — работаем бок о бок, миграция пользователей постепенная.

## 2. Что есть в эталоне (prodflow) и статус реализации

| Контур | Статус в prodflow | Судьба в PRODPLAN |
|---|---|---|
| Барабан: программа, выравнивание, слоты 🟢🟡🔴, гейт комплектности, релиз дня, roll-forward, авто-продление | реализован полностью | Фаза 1 (порт) |
| Питатель №2 «Мехцех»: позиции супермаркета, ADU/зоны, live-NFP, сигналы (Пополнение / Под график / Цепочка), kit-форс, очередь, full-kit гейт, обеспеченность, загрузка групп | реализован полностью | Фаза 2 (порт) |
| Питатель №4 «Закупка»: буферы закупных, сигналы + Purchase Plan → заявки | частично (сегмент A) | Фаза 3 (порт + доделка) |
| Питатель №3 «Гальваника»: давальческий round-trip, «у подрядчика» в NFP | только в доках | Фаза 4 (greenfield по докам) |
| Динамический пересайзинг зон, замер фактического RT, сегмент B закупки | только в доках | Бэклог после запуска |

Ключевые первоисточники: `prodflow/prodflow/services/drum/*`, `services/feeder/*`,
`services/purchase_plan.py`, `api.py`; методики — `техдизайн-фаза-1-барабан.md`,
`техдизайн-фаза-2-мехцех.md`, `питатель-{2,3,4}-*.md`, `дизайн-обеспеченность-и-цепочка-мехцеха.md`,
`дизайн-интерфейса-новой-системы-планирования.md`, `пакет-передачи-в-разработку.md`.

**Козырь переноса:** расчётные ядра prodflow — чистый Python без Frappe
(`drum/leveling.py`, `drum/kit_gate.py`, `feeder/zones.py`, `feeder/nfp_core.py`,
`feeder/chain.py`, `feeder/availability.py`, `feeder/adu.py`, `feeder/rollforward.py` и т.д.)
с pytest-тестами. Их переносим почти дословно; переписываются только адаптеры
(Frappe ORM → SQLAlchemy, doc-events → синк-триггеры).

## 3. Архитектура параллельного модуля в PRODPLAN

### 3.1. Бэкенд

- Роутер `backend/app/routers/dbr.py`, префикс `/api/v1/dbr`, регистрация в `main.py`
  (единый паттерн остальных роутеров).
- Пакет `backend/app/services/dbr/`:
  - `core/` — перенесённые чистые ядра (leveling, zones, nfp, kit_gate, chain, availability,
    rollforward) без SQLAlchemy — как в эталоне, тестируются без БД;
  - `adapters/` — чтение входов из общих таблиц (снимок в одной транзакции);
  - `program.py`, `drum.py`, `gate.py`, `release.py`, `positions.py`, `signals.py`,
    `queue.py`, `purchase.py` — оркестрация поверх ядер.
- Собственные таблицы `dbr_*` (ORM-модели в `models.py` + alembic-миграция; `create_all`
  несущий, модели SQLite-совместимые через `CrossPlatformJSON`).
- В общие таблицы модуль НЕ пишет (фазы 1–3 без материализации; материализация — через
  существующие экспортёры с маркером `source='dbr'`).

### 3.2. Маппинг данных ERPNext → PRODPLAN (входы уже в БД)

| prodflow (ERPNext) | PRODPLAN |
|---|---|
| Item (+custom_artikul, lead_time_days, optimal_batch, способ пополнения) | `items` (`item_code`, `replenishment_time`, `optimal_batch`, `replenishment_method`) |
| BOM / BOM Item / BOM Operation | `specifications` / `spec_components` / `spec_operations` (+`default_specifications`) |
| Workstation (+custom_wip_warehouse / custom_production_warehouse) | `production_resources` + `workshop_warehouse_bindings` (`warehouse_ref1c` = WIP-склад, `production_warehouse_ref1c` = склад выпуска; на проде заполнены для всех 16 участков) |
| Планировочные склады / игнорируемые | `stock_warehouses.is_selected` (20 на проде) + `ignored_warehouses` (32 на проде) — редактируются в настройках журнала исполнения (`/api/v1/production-control/settings`) |
| Holiday List | `work_calendar_day` |
| Bin.actual_qty | `item_warehouse_stock` (+`stock_warehouses`, `ignored_warehouses`) |
| Открытые WO (пополнение) | `production_orders` / `production_products` (`remaining_qty`) |
| Открытые PO (пополнение) | `supplier_orders` / `supplier_order_items` (`remaining_qty`) |
| MR/WO/PO при материализации | экспортёры `one_c_production_order_export`, `one_c_purchase_order_export` + `sync_link` |

### 3.3. Новые таблицы (по DocType эталона)

- `dbr_settings` (конфиг: горизонт гейта, склады №2/№3/№4, группы метизов, классы
  RT, batch_days, порог полки, k_var/k_crit, страховка риска по категориям, флаг цепочки).
  **Начальные значения импортируются из ERPNext prodflow** (`ProdFlow Planning Settings`,
  `ProdFlow Assembly Settings`) одноразовым скриптом — настройки там боевые, выверенные;
- `dbr_assembly_rate` (такты сборки: участок × SKU × шт/день) — **данные тоже импортируются
  из prodflow** (`ProdFlow Assembly Rate`); участки маппятся на `production_resources`
  (состав участков в обеих системах одинаков), SKU — по артикулу/коду 1С;
- `dbr_production_program` + `dbr_production_program_item`;
- `dbr_drum_schedule` + `dbr_drum_slot` + `dbr_drum_capacity_gap`;
- `dbr_supermarket_position`;
- `dbr_feeder_signal`;
- `dbr_purchase_plan` + `dbr_purchase_plan_item`;
- служебные: `dbr_run_lock` (advisory-lock прогона), журнал пересчётов.

### 3.4. Триггеры пересчёта (вместо doc-events Frappe)

В PRODPLAN нет событий документов — есть синк-джобы. Схема:
- после завершения `stock` / `productionOrders` / `supplierOrders` синка — инкрементальный
  пересчёт NFP и гейта (хук в `sync_orchestrator.tick` или отдельная DBR-джоба в `SYNC_JOBS`);
- ежечасный полный refresh (NFP + сигналы + гейт) — аналог hourly-планировщика prodflow;
- ночные: roll-forward слотов (03:00), авто-продление горизонта (03:30) — в тот же оркестратор;
- расчёты — короткими транзакциями по снимку, со своим advisory-lock, чтобы не пересекаться
  с `run_planning_run` и синками.

### 3.5. Фронтенд (frontend-erp-shell)

Новый раздел «Планирование DBR» (пункт в `navItems` + Route в `src/ui/App.tsx`), страницы по
эталонным (`prodflow_drum_board`, `prodflow_feeder_queue`, `prodflow_feeder_load`):
- `DbrProgramPage` — программы выпуска (создание/утверждение/исполнение);
- `DbrDrumBoardPage` — борд барабана: плитки по дням/участкам, цвета гейта, разрывы мощности,
  drag-move, релиз дня;
- `DbrFeederQueuePage` — очередь мехцеха: сигналы, приоритеты, обеспеченность, запуск/отмена;
- `DbrFeederLoadPage` — гистограмма загрузки групп оборудования;
- `DbrPurchasePage` — корзина закупки / purchase plan.
Мокапы и дизайн UI — `дизайн-интерфейса-новой-системы-планирования.md`,
`мокап-очередь-мехцеха-v2.html` в эталоне.

## 4. Фазы

### Фаза 0 — фундамент (≈1 неделя)
Ветка `feat/dbr-module`. Скелет: роутер, пакет `services/dbr/`, таблицы `dbr_settings`,
`dbr_assembly_rate`, миграция, раздел UI-заглушка. Перенос чистых ядер из prodflow вместе с их
pytest-тестами (адаптация импортов). Одноразовый импорт настроек и тактов из прод-ERPNext
(`tools/import_dbr_settings_from_erpnext.py`: Planning Settings, Assembly Rates, категорийная
страховка риска) с маппингом участков на `production_resources` и складов на
`stock_warehouses`. Критерий: тесты ядер зелёные в CI PRODPLAN, импортированные настройки
видны через `GET /api/v1/dbr/settings`.

### Фаза 1 — Барабан (≈2–3 недели)
Программа выпуска → выравнивание (`leveling.level`) → график/слоты/разрывы → гейт
комплектности (кит по `spec_components` до границ развязки №2/№3/№4/метизы, кумулятивный
netting остатков + открытого пополнения из `production_orders`/`supplier_orders`) → борд UI.
Roll-forward, авто-продление. Релиз дня в этой фазе — **без записи в 1С** (слот → статус
Released + черновик в `dbr_*`). Критерий: барабан на реальных данных прода в read-only,
план сходится с ручными ожиданиями ПДО.

### Фаза 2 — Питатель «Мехцех» (≈2–3 недели)
Генерация позиций супермаркета (многоуровневый разворот спроса, ADU от плана барабана, зоны),
live-NFP, сигналы (Пополнение / Под график / Цепочка), kit-форс, очередь с сортировкой и
материальной готовностью, агрегат дефицитов, загрузка групп. UI очереди. Критерий: очередь
мехцеха совпадает по логике с эталонными тестами prodflow; мастер видит и понимает очередь.

### Фаза 3 — Материализация и закупка (≈2 недели)
Запуск сигнала/релиз дня → создание заказа на производство в 1С через
`one_c_production_order_export` (идемпотентно, `sync_link`, `source='dbr'`). Экспортные
модули штатно работают в бою — пилотная группа номенклатуры не нужна, dry-run только как
предпросмотр перед проводкой. Purchase Plan + сигналы закупных буферов →
`one_c_purchase_order_export`. Обратная связь: синк заказов из 1С двигает статусы
слотов/сигналов (аналог `slot_progress`/`on_work_order_change`).
Критерий: полный цикл сигнал→заказ 1С→факт→гашение сигнала.

### Фаза 4 — Гальваника round-trip (≈2 недели, по докам)
Манифест рейса, слагаемое NFP «у подрядчика», алерты кругорейса — по
`питатель-3-гальваника-round-trip.md` (в эталоне не реализовано, проектируем сразу в PRODPLAN).

### Фаза 5 — параллельная эксплуатация и сведение
Shadow-режим: DBR и текущий MRP работают одновременно, страница сравнения рекомендаций.
Регламент: кто чем пользуется, какие участки переводим на очередь DBR первыми. Договориться о
разделении ответственности с `mrp_reconciliation` (пока DBR не материализует — конфликтов нет;
после фазы 3 — либо исключаем пилотную номенклатуру из reconcile, либо reconcile учится не
трогать `source='dbr'`). Критерии переключения и план вывода legacy-контура — отдельным
решением после пилота.

## 5. Решённые вопросы (ответы от 2026-07-16)

1. **Такты сборки** — берём из ERPNext prodflow (`ProdFlow Assembly Settings/Rate`,
   `Planning Settings`): одноразовый импорт-скрипт в фазе 0 (REST ERPNext или дамп MariaDB,
   доступы в `prodflow-erpnext/ERPnext/.docs/erpnext-deploy.md`). Настройки участков и
   мощностей в обеих системах аналогичны — маппинг участков 1:1 по именам.
2. **Маппинг складов** — уже есть в настройках журнала исполнения:
   `workshop_warehouse_bindings` (WIP + склад выпуска на участок, все 16 участков заполнены),
   `ignored_warehouses`, `stock_warehouses.is_selected`. Склады синхронизируются из 1С и
   совпадают с ERPNext полностью. DBR-модуль ничего своего не заводит — читает эти же таблицы;
   в `dbr_settings` остаются только роли «полок» (№2/№3/№4 → конкретные `warehouse_ref1c`).
3. **MOQ** — в 1С нет, не тянем (фича ERPNext). Зелёная зона закупных = `optimal_batch`/
   `ADU × batch_days`, без MOQ-подпорки.
4. **Привязки участков** (по виду производства, `resource_production_kinds`) — работают,
   классификатор кита использует их же. Запись в 1С — существующими модулями
   (`one_c_*_export`), они проверены: документы в 1С открываются и проводятся.

Факты с прода (проверено по API 2026-07-16): 16 участков; сборочные — снегоходы (cap 8),
мотобуксировщики (3), модули/пластик/навесные (2), двигатели/передний узел/балансиры (1) —
кандидаты в барабан; мехцех — токарный (3, buffer 21), токарный ЧПУ (2, 7), фрезерный (1, 5),
гибка (1, 21), сварка (6, 14), заготовительный (3, 30), окраска (3, 5) — контур питателя №2.
`buffer_days` участков фактически повторяют RT-классы prodflow (7/15/21) — при импорте
настроек сверить и взять за основу RT.

Снимок боевых настроек prodflow (прод ERPNext, 2026-07-16, `tabSingles`/`tabProdFlow Assembly
Rate`): такты — 64 записи по сборочным участкам (снегоходы 1 шт/день·ёмк., мотобуксировщики
3–4, модули 5–10); RT-классы: мехобработка 7, +сварка 15, +окраска 21 дн; batch_days: токарка
10, гибка 7, сварка 5, окраска чёрная 2 / цветная 3; frozen_days 3; горизонт гейта 10 раб.
дн; порог полки 5 шт; цепочка включена; горизонт загрузки 4 нед. Полки: Склад №2 = НФ-000092
(мехцех, WIP-буфер), Склад №3 = НФ-000112 (покрашенные детали), Склад №4 = НФ-000102 (корпус
№2) — все три есть в `stock_warehouses` PRODPLAN (склады синхронизируются и совпадают).

## 5а. Открытые вопросы (осталось)

1. Каким транспортом делать импорт из ERPNext: REST (порт 8080 доступен) или дамп MariaDB —
   решить в фазе 0 по факту.

Пилотная группа номенклатуры НЕ нужна (решение 2026-07-16): экспорт в 1С штатно работает,

## 5б. Приоритет (уточнение 2026-07-16)

Главная цель ближайших фаз — **просчёт барабана и его визуализация** (фазы 0–1: расчётное
ядро + борд с плитками, гейтом и разрывами мощности). Материализация в 1С и питатели — следом;
инфраструктура записи готова и проверена.

## 6. Принципы (несущие)

- Test-first: каждое перенесённое ядро приезжает со своими тестами; адаптеры и роутеры —
  pytest на SQLite (`tests/services/dbr/`, `tests/routers/`).
- Существующий контур не трогаем; общие таблицы для DBR — read-only до фазы 3.
- Все записи в 1С — через существующие экспортёры, идемпотентно (`sync_link`), сначала dry-run.
- Новые таблицы: ORM-модель + alembic-миграция одновременно (`create_all` несущий).
- Прод впереди локали: перед любой работой `git fetch` и сверка с origin/main.
