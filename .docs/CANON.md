# КАНОН PRODPLAN

Этот файл обязателен для любого изменения системы. У каждой величины один
источник истины и один владелец расчёта. Параллельные движки запрещены.
Канон появился после аудита 2026-07-25: четыре движка исполнения и пять
копий витринной математики стоили проекту двух суток работы двух моделей.

Действующие решения владельца хранятся только в
[`.docs/notes/mrp-decisions-log.md`](notes/mrp-decisions-log.md). При
противоречии код и остальные документы исправляются по журналу решений.
Пометка «§N» ниже — раздел этого журнала. Копии на рабочих станциях
вторичны; абсолютные машинные пути в документации запрещены.

## Ядро системы

PRODPLAN состоит из четырёх последовательно связанных контуров:

1. **План** фиксирует требуемый выпуск готовых изделий.
2. **MRP и Ledger резервов** разворачивают BOM для закреплённого за данным
   MRP количества корней, фиксируют полные резервы и потребности пополнения.
   У одного плана могут последовательно существовать несколько исторических
   MRP, но одновременно жив только один.
3. **Журналы пополнения** показывают одну потребность, разделённую по способу
   пополнения `make` или `buy`.
4. **Очередь сборки и барабан** раскладывают во времени незакрытый выпуск
   готовых изделий всех живых планов.

Ни один нижестоящий контур не пересчитывает величины вышестоящего.
В Ledger две ленты (§2, §12.5): резервы и заказы — план; производство и
остаток — факт.

## Единственные источники

| Величина | Единственный источник |
|---|---|
| Физическое движение и остаток | принятое поколение Item Ledger (§2, §11) |
| Исходный выпуск плана | зафиксированные строки периодного плана (§3) |
| Полная потребность BOM | зафиксированный `MrpRequirement` (§3, §4) |
| Резерв плана | `ReservationEntry` (§4) |
| Потребность пополнения | зафиксированное поле резерва (§5) |
| Выполнение пополнения | адресное назначение в пределах точно связанного живого резерва, затем единый FIFO (§5, §6, §12.6) |
| Выполнение и остаток выпуска плана | сохранённый накопленный принятый выпуск; остаток фиксируется как исходный выпуск минус этот факт и не пересчитывается при чтении (§3, §7) |
| Изменение спецификации живого плана | матрица и факт плана не меняются; старый MRP закрывается, все его живые резервы закрываются/освобождаются, а новый MRP того же плана получает сохранённый остаток корней и новую BOM (§3, §7) |
| Коррекция после смены MRP | по каждой детали сравниваются сохранённый незакрытый спрос старого MRP и потребность нового MRP; разница добавляет либо снимает рабочее количество (§3, §7) |
| Очередь сборки | остатки выпуска всех живых планов, oldest-first (§7) |
| Календарная раскладка сборки | единственный барабан поверх очереди сборки с сохранённым readiness gate (§8, §29) |
| Цель полки | расход барабана внутри защитного окна, ограниченный MRP (§10) |
| Количество вытягивания мехцеха | незакрытая MRP-потребность, ограниченная дефицитом полки (§10) |
| Исполнительный заказ | единый производственный или закупочный журнал (§1.6) |
| Количество локального MRP-заказа до выгрузки и исполнения | текущий сохранённый остаток MAKE по ключу «план + деталь»; согласованный obligation refresh автоматически приводит к нему ещё не затронутую однострочную локальную строку, не меняя резерв и потребность (§12) |
| Факт выпуска | считанный назад результат проведения `СборкаЗапасов` в принятом Item Ledger; это ПОСТУПЛЕНИЕ НА СКЛАД, а не завершение заказа (§1.6, §12.2) |
| Жизненный цикл заказа | создание: команда оператора из PRODPLAN → заказ в 1С. Исполнение: поступления гасят потребность и больше ничего не значат. Закрытие: только кнопка оператора — в PRODPLAN через санкционированный экспорт либо односторонне в 1С (read-back). Автоматического закрытия не существует (§12.1–12.4) |
| Судьба резерва при поступлении | точная связь сначала гасит связанный живой резерв, излишек идёт FIFO; факт без точной связи, по неизвестному PRODPLAN заказу 1С или по закрытому резерву идёт FIFO; существующий заказ 1С поступлением не закрывается и не удаляется; frozen-величины резерва не переписываются (§6, §12.6) |
| Отрицательный остаток на cutoff | в пуле распределения заморозки — 0 до пополнения; физический минус сохраняется в базисе и подсвечивается предупреждением (§13) |
| Связь агрегированной строки закупки с резервами | сохранённые `PurchaseExportObligationAllocation`; связанные живые резервы oldest-first в пределах экспортного `allocated_qty`, затем общий FIFO (§14) |
| Размотка возврата поставщику | исходное поступление точно; иначе та же строка заказа newest-first, затем глобально newest-first; без связи глобально newest-first (§15) |
| Свободный S0 нового плана | принятый физический остаток минус динамические удержания старших живых резервов; удержание освобождает только назначенный физический расход (§16) |
| Срок пополнения MRP | `Item.replenishment_time`, синхронизированный из `СрокПополнения` 1С; ноль валиден (§17) |
| Учётная цена номенклатуры | nullable `Item.accounting_price`, синхронизированный из последнего среза регистра `ЦеныНоменклатуры` 1С по виду цен «Учётная цена»; отсутствие цены остаётся `NULL`, а не нулём |
| Защитное окно полки | отдельный `ShelfPolicy.replenishment_time_days`; не подменяет срок MRP (§17) |
| Живая область планов поколения и привязка run | sealed-цепочка `parent_generation_id`: манифест `obligation_refresh` либо унаследованная область фактового форка; run жив при привязке внутри цепочки и cutoff, равном cutoff его поколения-анкера (§27) |
| Маршрут пополнения | только явно распознанный маршрут; пустое и неизвестное дают `unavailable` и блокируют публикацию. Явная «Переработка» создаёт сохранённый `rework`-резерв без `PlannedOrder`/`PlannedPurchase`/журнальной строки; маршрут и исполнение показываются `unavailable`, но принятый `assembly_in` адресно, затем FIFO закрывает такой резерв (§18) |

удалена как второе legacy-хранилище; синхронизация 1С публикует физику только
через жизненный цикл Item Ledger.

Команда `Произвести` является каноническим исполнительным контуром: одним
действием она создаёт в 1С `СборкаЗапасов` и `СдельныйНаряд`. Создание
документов не считается фактом; факт появляется только после read-back
регистра проведения в Item Ledger и адресно-FIFO выполнения резервов. Удаление
этого контура запрещено.

## Неподвижное и подвижное

После фиксации плана неподвижны:

- строки выпуска плана;
- результат BOM-развёртки;
- полный резерв;
- покрытие наличием на cutoff;
- исходная потребность пополнения.

С поступлением фактов меняются только:

- покрытая часть потребности пополнения;
- остаток выпуска плана;
- положение незакрытого выпуска в барабане;
- состояние исполнительных заказов.

Количество ещё не выгруженного и не затронутого исполнением локального
MRP-заказа является подвижной проекцией: obligation refresh приводит его вверх
или вниз к текущему незапущенному остатку MAKE того же плана и детали. Любая
попытка выгрузки, движение материалов, выпуск либо связь исполнительной цепочки
делает строку неподвижной; положительная разница после этого остаётся отдельным
предложением журнала.

Динамическое удержание старшего резерва для экранирования S0 также меняется
только принятым назначенным расходом. Это проекция Ledger, а не изменение
`reserved_qty`, покрытия на cutoff или исходной потребности пополнения (§16).

## Запрещено

- изменять матрицу зафиксированного плана или создавать план «/ остаток» при
  изменении спецификации;
- повторно считать уже закрытый MRP; specification-rebase закрывает его и
  создаёт новый MRP того же плана только на сохранённый остаток корней;
- держать одновременно несколько живых MRP одного плана;
- привязывать резерв непосредственно к плану, минуя MRP;
- заново вычислять накопленный факт плана в GET, refresh или
  specification-rebase;
- переносить журнал исполнения старого MRP в новый MRP;
- пересчитывать исходную потребность при refresh или поступлении;
- считать выполнение по статусам и накопительным полям заказов;
- писать состояние заказа 1С (`СостояниеЗаказа`, `ВариантЗавершения`)
  автоматически — скриптом, фоновым процессом или «согласователем»; запись
  состояния допустима только по явному нажатию кнопки оператором через
  санкционированную точку экспорта, одностороннее закрытие в 1С — read-back
  (§12.3–12.4);
- создавать ручную производственную программу для барабана;
- строить барабан по одному выбранному плану или `program_id`;
- создавать отдельный спрос, NFP или буфер сверх MRP-потребности;
- строить кросс-валидатор двух копий одной величины — это тоже дубль;
- резолвить живой run строгим равенством `PlanningRun.ledger_generation_id` и
  принятого поколения либо сравнением его `ledger_cutoff` с текущим cutoff:
  фактовый форк не переанкоривает обязательство (§27);
- переанкоривать retained-run или строки его обязательства при фактовом форке;
- обходить sealed-цепочку `parent_generation_id` где-либо, кроме
  `live_plan_scope.py`;
- терять невыполненную плитку при смене даты или поколения;
- приписывать физический факт произвольному заказу;
- считать поступление освобождением удержанного старшим резервом склада;
- подменять пустой или неизвестный способ пополнения производством;
- заменять MRP-срок из 1С локальной настройкой полки;
- использовать legacy-таблицу как fallback;
- сохранять в живой документации отменённую модель.

## Правила расширения

1. Новая функция читает существующую величину, а не вычисляет её второй раз.
2. Новый способ пополнения расширяет маршрутизацию, но не формулу потребности.
3. Оптимизаторы запуска, комплектности и раскроя ограничивают исполнение уже
   существующей потребностью; новый спрос они не создают.
4. DBR может менять срок, приоритет и удерживаемую на полке часть потребности,
   но не её общее количество.
5. Проекция и UI не содержат бизнес-математики.
6. Замена пути включает удаление старого пути и его документации в той же
   волне; сохранение легаси «за флагом» — только решением владельца с датой
   сноса.
7. Непринятый, неполный или stale Ledger даёт `unavailable`, а не ноль.

## Фронтенд

Фронтенд собирается как единый типизированный ERP-каркас. Одна backend-
сущность получает одно frontend-представление; разные рабочие места являются
режимами и фильтрами.

OpenAPI — источник транспортных типов. Страницы не вызывают HTTP напрямую,
не пересчитывают backend-величины и не создают собственные копии планов,
журналов или очередей. Контракт:
[`frontend-framework.md`](frontend-framework.md).

Любые предметные суммы, остатки, проценты, статусы, приоритеты, KPI,
группировки и доступные действия приходят готовыми из сохранённой backend
read-model. Frontend выполняет только форматирование и управление интерфейсом.

## Приёмка

Изменение принимается только если тесты доказывают:

- неизменность зафиксированного плана и резервов;
- один адресно-FIFO алгоритм без двойного зачёта;
- сохранение незакрытого выпуска в очереди;
- детерминированную раскладку барабана;
- отсутствие ручного или параллельного источника спроса;
- fail-closed без legacy fallback.

Гейт волны — полный pytest с ФИНАЛЬНОГО коммита волны; цифра, снятая с
другого состояния кода, — ложь.

## Механическая проверка

`tests/test_canon_invariants.py` существует и уже фиксирует непротиворечивость
действующих документов: наличие журнала решений и реестра владельцев,
канонические формулы и имена полей, отсутствие ссылок на удалённые контракты и
возврата отменённых пользовательских сценариев. Доки владельца читаются из
`.docs/notes/`; их отсутствие — падение теста, а не молчаливый пропуск.

Файл включён в обязательный CI: workflow `.github/workflows/canon.yml` гоняет
`pytest -q tests/test_canon_invariants.py` в job `canon-invariants`, от которого
зависят job'ы `backend` и `frontend` — красный канон блокирует весь прогон.

До покрытия перечисленных ниже архитектурных инвариантов сведение кода ядра
не считается завершённым:

- фиксированный список писателей `ReservationEvent`;
- единственные точки записи документов в 1С;
- отсутствие второго хранилища физических остатков;
- отсутствие второго вычислителя reserve/replenishment/execution;
- отсутствие ручных DBR-программ и `program_id` как источника барабана;
- отсутствие предметной математики и прямого HTTP в frontend UI;
- один живой канонический `planning_run` на фиксированный план и неизменяемая
  цепочка закрытых исторических run этого же плана;
- отсутствие ссылок на несуществующую документацию.
