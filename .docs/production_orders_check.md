# Учет заказов на производство при расчете потребностей

## Текущая ситуация
При формировании новых заказов на производство система не учитывает уже существующие активные заказы, что может приводить к избыточному планированию.

## Требование
Необходимо внести изменения в логику расчета потребностей таким образом, чтобы при формировании новых заказов учитывались все активные заказы на производство, за исключением заказов со статусом "Закрыт".

## Термины и статусы (зафиксировать в коде/БД)

### Что считаем «активным заказом»
- **Активный** — заказ, который должен участвовать в расчетах потребностей (не закрыт).
- **Закрыт** — заказ, который **не** должен участвовать в расчетах.

### Важно: поле `is_posted`
В текущем описании поле `is_posted` трактуется как «закрыт/не закрыт»:
- `is_posted = FALSE` — **активный** (учитывать)
- `is_posted = TRUE` — **закрыт** (не учитывать)

Примечание: в типовой терминологии 1С «posted/проведён» ≠ «закрыт». Перед реализацией нужно **подтвердить**, что именно означает `is_posted` в контексте `production_orders` и соответствует ли оно статусу «Закрыт» из требования.

## Область учёта активных заказов (A/B)
Чтобы требование было однозначным, фиксируем, что активные заказы учитываются **в двух местах**:

**A) Как уже запланированный выпуск готовой продукции**
- Если на изделие уже есть активные заказы, то новая потребность на выпуск этого же изделия должна быть уменьшена на количество активных заказов (в пределах горизонта расчёта, если он применяется).

**B) Как потребление компонентов (резервирование остатков)**
- Активные заказы потребляют компоненты по спецификации и тем самым уменьшают доступные остатки/доступность компонентов для новых заказов.

Если в дальнейшем решим учитывать только A или только B — это нужно явно отразить в документе (и в тест-кейсах).

## Подробности реализации

### 1. Источник данных
- Заказы на производство синхронизируются из 1С по сущности `Document_ЗаказНаПроизводство`
- В БД хранятся в таблице `production_orders`
- Статус заказа отражается в поле `is_posted` (булевое значение)

Дополнительно (уточнить при реализации):
- Какие поля количества используются для «кол-во к выпуску/заказано/выпущено/отменено» (чтобы корректно учитывать частично выполненные заказы).
- Есть ли разрез по организации/складу/подразделению и нужно ли ограничивать выборку активных заказов этим разрезом.

### 2. Логика фильтрации
- При расчете потребностей учитываются все заказы, у которых `is_posted = FALSE` (не закрытые)
- Заказы с `is_posted = TRUE` считаются закрытыми и не учитываются в расчетах

Рекомендуется явно фиксировать в коде/тестах:
- что происходит с заказами в статусах «Отменён/Аннулирован/Не актуален» (если такие статусы есть в 1С и попадают в БД);
- как обрабатываются частично выполненные заказы (учитывать остаток к выпуску/к обеспечению).

### 3. Место в коде
Основные изменения должны быть внесены в:
- `backend/app/services/order_quantity_calculator.py` - класс `OrderQuantityCalculator`
- В метод `_limit_by_components` добавить проверку на активные заказы
- В метод `compute` добавить учет активных заказов в суммарной потребности

### 4. Алгоритм учета активных заказов
0. Входные данные (для расчёта по изделию X):
   - плановая потребность (новая) по X;
   - остатки/доступность компонентов;
   - список активных заказов.

1. Получить список всех активных заказов (по текущим правилам фильтрации).

2. Учет области A (выпуск готовой продукции):
   - Суммировать количество активных заказов на изделие X.
   - Уменьшить «новую потребность» на эту величину (не уходя в отрицательные значения).

3. Учет области B (потребление компонентов активными заказами):
   - Для каждого активного заказа определить потребность в компонентах через спецификацию.
   - Суммировать потребность в компонентах по всем активным заказам.
   - Считать, что эти количества «занимают» остатки (т.е. уменьшают доступность компонентов для нового заказа).

4. Рассчитать максимально возможное количество для нового заказа по X с учетом:
   - доступности компонентов после «занятия» активными заказами;
   - правил округления/дискретности единиц измерения.

### 5. Особенности
- Учитывать только те компоненты, которые связаны с активными заказами через спецификации
- Правило распределения остатков: **сначала** покрыть потребление компонентов активных заказов, **затем** потребление нового заказа
- Для дискретных единиц измерения (шт, pcs) использовать целочисленные расчеты

Edge-cases (добавить в реализацию/тесты):
- активный заказ без найденной спецификации (ошибка/варнинг/пропуск — выбрать поведение);
- спецификация изменилась с момента создания активного заказа (использовать «зафиксированную» или актуальную — выбрать правило);
- отрицательная потребность после учета области A (обнулять);
- смешанные единицы измерения и округления.

### 6. Влияние на другие модули
- Модуль синхронизации `production_order_sync.py` должен корректно обновлять статусы заказов
- Модуль планирования `planning_service.py` должен использовать обновленный калькулятор
- Необходимо обновить юнит-тесты для отражения новой логики

## Чек-лист проверок / тест-кейсы

### Сценарии (минимум)
1. **Есть активный заказ на изделие X**
   - Ожидание: новая потребность по X уменьшается на кол-во активного заказа (область A).

2. **Есть закрытый заказ на изделие X**
   - Ожидание: закрытый заказ игнорируется (не влияет ни на A, ни на B).

3. **Два активных заказа на разные изделия, пересекающиеся по компонентам**
   - Ожидание: суммарное потребление компонентов активными заказами уменьшает доступность компонентов для нового заказа (область B).

4. **Дискретные единицы (шт/pcs)**
   - Ожидание: итоговые количества для нового заказа и/или компонентов целочисленные, округление предсказуемо.

5. **Активный заказ без спецификации / спецификация не найдена**
   - Ожидание: выбранное поведение зафиксировано (например: варнинг и пропуск или ошибка и останов).
