# Документ для правки кода: «Отчёт о выпуске техники» + дневное закрытие + перенос остатков

Дата: 2026-02-06

## 1) Контекст и текущая проблема

### 1.1. Наблюдение бизнеса

Если план выпуска корневого изделия не выполнен в срок, то при «ежедневном автоматическом сдвиге» потребность может визуально/логически пропадать.

### 1.2. Что сейчас происходит в коде (фактический механизм «сдвига»)

В текущем UI «План выпуска техники дневной» окно по умолчанию всегда строится от **сегодня**:

- фронтенд отправляет `start_date = today` в [`PlanPage.loadPlanData()`](frontend/src/pages/PlanPage.vue:366);
- далее на клиенте ещё и отбрасываются прошлые даты через `futureDates = allDates.filter(d => d >= todayStr)` в той же функции ([`PlanPage.loadPlanData()`](frontend/src/pages/PlanPage.vue:381)).

В результате:

- плановые количества, которые стоят на прошлых днях, **исчезают из видимой матрицы**;
- если фактического выпуска не было и остаток не перенесён вперёд, то для пользователя/процессов создаётся эффект «план сдвинулся, потребность исчезла».

Плановые записи хранятся в [`ProductionPlanEntry`](backend/app/models.py:293) (колонки `planned_qty` и `completed_qty`).

## 2) Целевой процесс (принят по решениям)

Источник правды по принятым правилам: [`.docs/weekly_production_report_decisions.md`](.docs/weekly_production_report_decisions.md:1).

### 2.1. Недельный отчёт — основной экран контроля

Нужна новая страница/таблица «Отчёт о выпуске техники недельный», которая:

- показывает неделю **Пн–Вс** (включая Сб/Вс);
- позволяет вносить факт выпуска по дням;
- считает «остаток»;
- содержит действие «Закрыть день».

Выходные:

- **Сб/Вс отображаются**, но **не требуют закрытия** и **пропускаются** при переносе.

### 2.2. Дневное закрытие вместо автоматического ежедневного “сдвига”

Вместо ежедневного автоматического сдвига окна (который фактически реализован как чтение от `today`), вводим правило:

1) Всегда закрывается **предыдущий рабочий день**: `D_close = previous_workday(today)`.
2) При закрытии считаем перенос по каждому изделию:

`carry_qty = max(plan_qty(D_close) - fact_qty(D_close), 0)`.

3) Перенос кладём на **рабочий день “через один” после today**:

`D_target = next_workday(next_workday(today))`.

Пример из решения: «сегодня вторник, закрываем понедельник → перенос на четверг».

4) Перенос **мерджится добавлением**:

`plan_qty(D_target) += carry_qty`.

5) Повторное закрытие допускается как **re-run**: откатить предыдущий перенос и применить новый.

6) После закрытия дня факт за `D_close` становится **read-only**.

7) Пропуски дней запрещены: нельзя закрывать более поздний рабочий день, пока не закрыты предыдущие (см. [`.docs/weekly_production_report_decisions.md`](.docs/weekly_production_report_decisions.md:29)).

## 3) Что нужно поменять в коде (план работ)

Ниже — целевое ТЗ для разработки (backend + frontend + БД), чтобы реализовать процесс из раздела 2.

### 3.1. БД: добавить сущности «закрытие дня» и «перенос»

Почему нельзя обойтись только `production_plan_entries.completed_qty`:

- нам нужно состояние «день закрыт» (read-only);
- нам нужен **audit/идемпотентность** для re-run;
- нам нужен **откат переносов** (иначе `+=` будет удваивать перенос при повторных закрытиях).

Предлагаемые таблицы:

1) `production_day_close`
   - `id`
   - `close_date` (DATE) — какой день закрываем (`D_close`)
   - `status` (например: OPEN/CLOSED)
   - `closed_at`, `closed_by`
   - `target_date` (DATE) — рассчитанная дата переноса `D_target` (фиксируем, чтобы re-run был воспроизводим)
   - `created_at`, `updated_at`

2) `production_day_close_item`
   - `id`
   - `day_close_id` (FK)
   - `item_id`
   - `planned_qty_snapshot` (DECIMAL)
   - `fact_qty_snapshot` (DECIMAL)
   - `carry_qty` (DECIMAL)
   - `applied_to_date` (DATE) — куда фактически применили перенос (обычно = `target_date`)

3) (опционально) `work_calendar_day`
   - `date` (DATE, PK)
   - `is_workday` (BOOL)
   - `comment`

Примечание: даже если на MVP календарь будет «Пн–Пт», таблица календаря сильно упростит выполнение решения «рабочие дни задаются календарём».

### 3.2. Backend: сервис календаря рабочих дней

Нужны функции:

- `is_workday(date) -> bool`
- `previous_workday(date) -> date`
- `next_workday(date) -> date`

Ссылка на аналогичную логику в проекте: в capacity-планировании уже есть обход рабочих дней в [`CapacityScheduler.allocate_backward()`](backend/app/services/capacity_scheduler.py:260), но там логика завязана на «ресурсные календари/настройки мощностей». Для отчёта нужен **глобальный календарь**, независимый от участков.

### 3.3. Backend: API для недельного отчёта

Добавить (или расширить) эндпоинты в [`plan.py`](backend/app/routers/plan.py:1):

1) Получение недельного отчёта:
   - `POST /v1/plan/production_report/week`
   - вход: `week_start` (YYYY-MM-DD) или `any_date_in_week`
   - выход:
     - список дней недели (Пн–Вс) + флаги `is_workday`
     - строки по изделиям:
       - `item_id`, `item_code`, `item_name`, `item_article`
       - `plan_by_day[date]`
       - `fact_by_day[date]`
       - `plan_week`, `fact_week`, `remaining_week`
       - статусы «день закрыт?» для дня `D_close` (и/или по всем дням)

2) Сохранение факта (без закрытия):
   - `POST /v1/plan/production_report/fact/bulk_upsert`
   - payload: `{ item_id, date, fact_qty }[]`
   - запись в `production_plan_entries.completed_qty` для соответствующих дат.

3) Закрытие дня:
   - `POST /v1/plan/production_report/day/close`
   - без входных параметров (день выводится из `today`) или с `close_date` (но решения требуют «строго предыдущий рабочий»)
   - выполняет алгоритм из раздела 2.2:
     - проверка пропусков,
     - снапшот план/факт,
     - расчёт переносов,
     - применение переносов через `planned_qty += carry_qty` на `D_target`,
     - фиксация/обновление `production_day_close`.

4) Re-run закрытия:
   - можно тем же эндпоинтом (если `production_day_close` уже есть) или отдельным `POST /day/rerun`.

### 3.4. Backend: алгоритм закрытия дня (псевдокод)

В одной транзакции:

1) `today = date.today()` (или TZ предприятия).
2) `D_close = previous_workday(today)`.
3) Проверить, что **нет незакрытых** рабочих дней раньше `D_close`.
4) Вычислить `D_target = next_workday(next_workday(today))`.
5) Найти/создать запись `production_day_close` для `D_close`.
6) Если это re-run:
   - загрузить `production_day_close_item` прошлого прогона;
   - для каждого item откатить: `planned_qty(D_target_prev) -= carry_qty_prev`;
   - очистить строки `production_day_close_item`.
7) Собрать набор изделий:
   - все изделия, у которых `planned_qty(D_close) > 0` или `fact_qty(D_close) > 0`.
8) Для каждого изделия:
   - `plan = planned_qty(D_close)`
   - `fact = completed_qty(D_close)`
   - `carry = max(plan - fact, 0)`
   - если `carry > 0`: `planned_qty(D_target) += carry`
   - записать снапшот в `production_day_close_item`.
9) Пометить `production_day_close.status = CLOSED`, зафиксировать `target_date = D_target`.

Отдельно: закрытые дни должны быть read-only на уровне API сохранения факта.

### 3.5. Frontend: новая страница отчёта

Добавить страницу (например, на основе стиля таблицы из [`PlanPage.vue`](frontend/src/pages/PlanPage.vue:1)):

- фиксированные 7 колонок дней недели + 2 агрегатных;
- ввод факта в ячейках;
- «Сохранить изменения» (bulk_upsert);
- «Закрыть день»:
  - показывает, какой день будет закрыт (D_close),
  - подтверждение,
  - после успеха перезагрузка недели.

Важно: UI должен показывать выходные, но не заставлять закрывать отчёт за Сб/Вс.

## 4) Тестирование (минимальный набор)

Backend unit/integration tests:

1) Закрытие дня переносит остаток на `D_target` с пропуском выходных/календаря.
2) Перевыпуск (fact > plan) не создаёт перенос.
3) Re-run:
   - сначала создаёт перенос,
   - затем при изменении факта откатывает старый перенос и применяет новый,
   - итоговый план на `D_target` корректный (без удвоения).
4) Пропуск дней: если не закрыт `D_close-1`, то закрытие `D_close` запрещено.

Frontend checks:

- корректные итоги «остаток недели»;
- read-only факт за закрытый день.

## 5) Риски и тонкие места

1) Даты в `production_plan_entries.date` — `DateTime` ([`ProductionPlanEntry`](backend/app/models.py:293)). Нужна строгая нормализация (например, хранить как полночь) и сравнения только по дате.
2) Календарь рабочих дней: без таблицы календаря вы быстро упираетесь в праздники/переносы.
3) Re-run обязателен, иначе при `+=` будет накапливаться перенос.
